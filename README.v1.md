# DataDock

**Your Data. One Workspace.**

一个轻量级、跨平台、多数据源管理工具。

DataDock 致力于为开发者提供统一、简洁、高效的本地数据库管理工作台。通过一个桌面应用管理不同类型的数据服务，减少开发过程中在多个数据库客户端之间切换的成本。

## 1. 项目介绍

DataDock 是一款基于 Tauri 构建的跨平台桌面数据库管理工具。

项目采用模块化架构设计，支持不同类型的数据源接入。用户可以通过统一的操作界面管理数据库连接、浏览数据、执行查询、查看数据结构以及进行数据维护。

项目以轻量化、易用性和开发者体验为核心，不追求复杂的企业级数据库运维功能，而是重点解决开发者日常开发过程中常见的数据管理需求。

### 核心目标

- 通过一个桌面应用统一管理多种数据源。
- 提供简洁、直观、符合程序员使用习惯的操作界面。
- 提供数据库连接、查询、数据浏览和结构管理能力。
- 尽可能减少应用自身的资源占用。
- 支持 Windows、macOS、Linux。
- 采用可扩展的数据源架构，方便后续接入新的数据库类型。
- 默认本地运行，不依赖云端服务。

## 3. 版本规划

DataDock 采用分阶段迭代方式开发。

### V1.0 - MySQL

第一阶段重点完成 MySQL 数据库管理能力，建立整个应用的基础架构。

核心功能：

- 数据库连接管理。
- MySQL 连接配置。
- 数据库、表、视图等对象浏览。
- SQL 编辑器。
- SQL 语法高亮。
- SQL 执行与结果展示。
- 数据表数据浏览。
- 数据分页查询。
- 数据新增、修改、删除。
- 表结构查看。
- 表字段、索引查看。
- 多连接管理。
- 查询历史记录。
- 本地配置持久化。

### V2.0 - Redis

第二阶段增加 Redis 数据源支持。

核心功能：

- Redis 连接管理。
- Redis 数据库切换。
- Key 浏览与搜索。
- Key 类型识别。
- String、List、Hash、Set、ZSet 数据查看。
- Key 新增、修改、删除。
- TTL 查看与修改。
- Redis 命令执行。
- 大量 Key 的分页或渐进式加载。

### V3.0 - PostgreSQL

第三阶段增加 PostgreSQL 数据源支持。

核心功能：

- PostgreSQL 连接管理。
- 数据库、Schema 浏览。
- 表、视图等对象浏览。
- SQL 编辑与执行。
- 查询结果展示。
- 表数据浏览与编辑。
- 表结构查看。
- 字段、索引、约束查看。
- 事务相关操作。

具体功能范围以对应版本的产品需求文档为准。

## 5. 架构设计原则

DataDock 采用前后端分离的桌面应用架构。

### 前端职责

- 页面展示与用户交互。
- 数据源连接管理界面。
- SQL 编辑器。
- 数据浏览与结果展示。
- 状态管理。
- 用户操作反馈。

### Rust 后端职责

- 数据库连接管理。
- 数据库驱动调用。
- SQL 执行。
- 数据库元数据读取。
- 数据结果处理。
- 本地文件与配置管理。
- 安全凭据管理。
- 数据源适配器管理。

### 核心架构原则

1. 前端不直接连接数据库。
2. 数据库连接和 SQL 执行由 Rust 后端统一管理。
3. 不同数据源采用独立适配器。
4. 业务功能尽量与具体数据库类型解耦。
5. 数据源之间不共享不兼容的数据库操作逻辑。
6. 通过统一的数据源接口提供基础能力。
7. 不为了未来扩展而提前实现尚未规划的功能。

## 6. UI 设计方向

DataDock 采用程序员熟悉的 IDE 风格设计。

整体参考现代代码编辑器和数据库开发工具的布局方式，而不是传统后台管理系统的布局。

主要设计特点：

- 左侧为资源管理区域。
- 中间为主要工作区域。
- 顶部为工具栏和标签页。
- SQL 编辑器采用代码编辑器风格。
- 查询结果采用表格形式展示。
- 支持多标签页。
- 支持深色和浅色主题。
- 合理利用屏幕空间。
- 界面简洁，减少不必要的装饰。

具体布局和交互规范以 UI 与交互设计文档为准。

## 7. 项目开发原则

### 7.1 版本控制

严格按照版本规划推进开发。

V1.0 只实现 MySQL，不提前开发 Redis 和 PostgreSQL 的具体功能。

### 7.2 模块化开发

各个业务模块应具备清晰的职责边界。

避免将数据库连接、SQL 执行、页面交互等逻辑全部堆积在单一模块中。

### 7.3 数据安全

- 数据库密码不得明文保存在普通配置文件中。
- 敏感信息应使用系统安全凭据存储机制。
- SQL 执行应考虑超时和取消。
- 数据修改操作应提供必要的确认机制。
- 默认只在本地保存应用配置和用户数据。

### 7.4 代码质量

- 保持代码结构清晰。
- 避免重复实现。
- 统一错误处理。
- 核心业务逻辑应具备测试。
- 新功能不得随意破坏已有功能。
- 不允许通过大量硬编码实现业务功能。

### 7.5 AI 辅助开发

本项目采用 AI 辅助开发方式。

AI 编码工具必须：

1. 开发前阅读项目相关文档。
2. 遵循既定的技术架构。
3. 按照任务拆分逐步实现。
4. 不得擅自修改核心架构。
5. 不得随意引入新的依赖。
6. 完成功能后执行必要的测试。
7. 更新对应的开发任务状态。
8. 遇到需求不明确或架构冲突时，先说明问题，不得自行扩大需求。
