# DataDock 核心模块设计

> 文档版本：V1.0
> 文档状态：核心模块设计
> 适用版本：V1.0（MySQL）
> 所属项目：DataDock

## 1. 文档说明

### 1.1 编写目的

本文档用于定义 DataDock V1.0 核心模块的职责、接口、数据流和实现规则。

重点解决以下问题：

1. 数据库连接如何创建、保存和管理？
2. 多个数据库连接如何相互隔离？
3. 数据源适配器如何设计？
4. SQL 如何执行、返回结果和取消？
5. 后台任务如何管理生命周期？
6. 表数据如何分页、筛选、排序和编辑？
7. 如何查询数据库结构？
8. 查询历史如何保存？
9. 数据如何导出？
10. 各模块之间如何协作？

### 1.2 设计范围

V1.0 只实现 MySQL。

本文件涉及：

| 模块                   | V1.0 是否实现 |
| ---------------------- | ------------- |
| 连接管理               | 是            |
| MySQL 数据源适配器     | 是            |
| 数据库资源查询         | 是            |
| SQL 执行               | 是            |
| SQL 任务管理           | 是            |
| 查询结果处理           | 是            |
| 表数据浏览             | 是            |
| 表数据新增、修改、删除 | 是            |
| 表结构查询             | 是            |
| 查询历史               | 是            |
| SQL 收藏               | 是            |
| CSV 导出               | 是            |
| JSON 导出              | 是            |
| Redis 适配器           | 否            |
| PostgreSQL 适配器      | 否            |
| SSH 隧道               | 暂不实现      |
| 数据库迁移             | 暂不实现      |

### 1.3 设计原则

- 每个模块职责明确。
- 模块之间通过明确接口通信。
- 不允许前端直接操作远程数据库。
- 数据库操作统一由 Rust 后端完成。
- 不允许将所有业务逻辑写在 Tauri Command 中。
- 不允许将所有数据库操作写在一个 MySQL 文件中。
- 多连接必须相互隔离。
- SQL 执行必须异步化。
- 所有重要操作必须具备错误处理。
- 不为尚未实现的数据源提前设计复杂业务逻辑。

## 3. 公共数据模型

不同模块之间需要统一数据结构，避免每个模块重复定义相同字段。

### 3.1 统一 ID

以下对象建议使用 UUID：

- connection_id
- task_id
- history_id
- favorite_id
- workspace_id

统一使用字符串形式传递给前端。

### 3.2 数据源类型

V1.0 使用：

```
type DataSourceType = 'mysql';
```

未来扩展：

```
type DataSourceType =
  | 'mysql'
  | 'redis'
  | 'postgresql';
```

持久化时使用稳定字符串，不依赖 Rust 枚举的内部序列化格式。

### 3.3 连接配置

```
interface ConnectionConfig {
  id: string;
  name: string;
  sourceType: 'mysql';

  host: string;
  port: number;
  username: string;

  defaultDatabase?: string;
  charset?: string;

  connectTimeoutMs?: number;

  credentialKey?: string;

  createdAt: number;
  updatedAt: number;
}
```

注意：

- 不包含明文密码。
- `credentialKey` 是系统凭据引用。
- 密码通过后端 CredentialService 获取。
- 前端不应长期持有密码。
- 修改连接时，密码字段需要单独处理。

### 3.4 数据库连接状态

```
type ConnectionStatus =
  | 'disconnected'
  | 'connecting'
  | 'connected'
  | 'error';

interface ConnectionRuntimeInfo {
  connectionId: string;
  status: ConnectionStatus;
  currentDatabase?: string;
  connectedAt?: number;
  lastError?: string;
}
```

运行时状态只保存在后端内存和必要的前端状态中，不需要持久化所有运行时字段。

### 3.5 统一分页模型

```
interface PageRequest {
  page: number;
  pageSize: number;
}

interface PageResult<T> {
  items: T[];
  page: number;
  pageSize: number;
  total?: number;
  hasMore: boolean;
}
```

约束：

- page 从 1 开始。
- pageSize 必须大于 0。
- 后端必须限制最大 pageSize。
- total 可以为空，表示没有执行精确总数统计。
- hasMore 用于判断是否还有下一批数据。

### 3.6 统一数据库值类型

数据库返回值需要支持常见 MySQL 类型。

建议使用可序列化的数据值模型：

```
type DatabaseValue =
  | { type: 'null'; value: null }
  | { type: 'boolean'; value: boolean }
  | { type: 'integer'; value: string }
  | { type: 'float'; value: number }
  | { type: 'decimal'; value: string }
  | { type: 'string'; value: string }
  | { type: 'date'; value: string }
  | { type: 'datetime'; value: string }
  | { type: 'time'; value: string }
  | { type: 'json'; value: unknown }
  | { type: 'binary'; value: string };
```

说明：

1. 大整数建议使用字符串传输，避免 JavaScript Number 精度丢失。
2. DECIMAL 建议保留字符串精度。
3. NULL 必须和空字符串区分。
4. 二进制数据不能随意转换成普通文本。
5. 日期时间需要明确格式和时区策略。
6. 不支持的数据库类型需要有安全的降级展示方式。

Rust 后端应当建立对应的枚举和转换逻辑。

## 4. 数据源注册模块

### 4.1 模块职责

DataSourceRegistry 负责管理 DataDock 支持的数据源适配器。

V1.0 只注册 MySQLAdapter。

后续增加 Redis、PostgreSQL 时，通过注册新的适配器扩展。

### 4.2 核心接口

建议定义：

```
pub trait DataSourceAdapter: Send + Sync {
    fn source_type(&self) -> DataSourceType;

    async fn test_connection(
        &self,
        config: &ConnectionConfig,
        credential: &Credential,
    ) -> Result<ConnectionTestResult, AppError>;

    async fn create_runtime(
        &self,
        config: &ConnectionConfig,
        credential: &Credential,
    ) -> Result<Arc<dyn DataSourceRuntime>, AppError>;
}
```

运行时接口可以进一步抽象为：

```
pub trait DataSourceRuntime: Send + Sync {
    async fn close(&self) -> Result<(), AppError>;

    async fn health_check(&self) -> Result<bool, AppError>;
}
```

说明：

以上为设计示意。实际 Rust 异步 Trait 的实现方式需要结合最终使用的 async-trait 或 Rust 原生异步 Trait 能力确定。

不同数据源的操作能力不应全部塞进一个庞大的统一接口。

建议将 SQL 数据源专有能力放在独立的 SQL Adapter 接口中。

### 4.3 注册流程

```
应用启动
   |
   ▼
创建 DataSourceRegistry
   |
   ▼
注册 MySQLAdapter
   |
   ▼
ConnectionService 获取适配器
   |
   ▼
根据 source_type 执行对应操作
```

### 4.4 验收标准

- 可以注册 MySQLAdapter。
- 可以根据 source_type 获取适配器。
- 未注册的数据源返回明确错误。
- 连接管理模块不直接依赖具体 MySQL 实现细节。

## 5. 连接管理模块

### 5.1 模块职责

连接管理模块负责数据库连接配置、连接测试、连接建立、连接断开和运行时状态管理。

拆分为两个部分：

**ConnectionService**

负责连接相关业务。

**ConnectionManager**

负责运行时连接资源。

二者不能混为一谈。

### 5.2 ConnectionService

职责：

- 创建连接配置。
- 编辑连接配置。
- 删除连接配置。
- 查询连接配置列表。
- 测试数据库连接。
- 建立数据库连接。
- 断开数据库连接。
- 查询连接状态。

### 5.3 ConnectionManager

职责：

- 保存运行时连接实例。
- 根据 connection_id 获取连接。
- 管理连接状态。
- 释放连接资源。
- 管理连接关联的任务。
- 防止同一个连接被重复创建。
- 处理连接异常。

### 5.4 连接创建流程

```
用户填写连接信息
        |
        ▼
前端调用 create_connection
        |
        ▼
ConnectionService
        |
        ├── 校验连接参数
        |
        ├── 保存密码到系统凭据服务
        |
        ├── 保存连接配置到 SQLite
        |
        ▼
返回 connection_id
        |
        ▼
前端刷新连接列表
```

连接配置保存成功但凭据保存失败时，不能留下一个看似有效但无法使用的连接配置。

需要明确失败回滚策略。

### 5.5 测试连接流程

```
用户点击测试连接
        |
        ▼
test_connection
        |
        ▼
ConnectionService
        |
        ├── 参数校验
        ├── 获取对应 Adapter
        ├── 获取密码
        └── 创建临时连接
                |
                ▼
          MySQL Adapter
                |
          ┌─────┴─────┐
          ▼           ▼
        成功         失败
          |           |
          ▼           ▼
       返回结果    返回错误信息
```

测试连接不应当默认将连接保存到运行时 ConnectionManager。

临时连接完成测试后必须释放资源。

### 5.6 正式连接流程

```
用户点击连接
      |
      ▼
ConnectionService
      |
      ├── 检查连接配置
      ├── 检查当前状态
      ├── 获取凭据
      └── 获取数据源 Adapter
                |
                ▼
          创建运行时连接
                |
                ▼
          ConnectionManager
                |
                ▼
          保存连接实例
                |
                ▼
          更新状态
                |
                ▼
          通知前端
```

### 5.7 连接断开流程

断开连接前：

1. 阻止新任务提交。
2. 查找当前连接的活动任务。
3. 根据任务类型执行取消、等待或清理策略。
4. 释放数据库连接资源。
5. 清理运行时状态。
6. 通知前端。

如果连接仍有 SQL 正在执行，需要提供明确的处理策略，不能直接删除连接实例导致任务状态失控。

### 5.8 核心接口

| 接口                  | 说明           |
| --------------------- | -------------- |
| create_connection     | 创建连接配置   |
| update_connection     | 修改连接配置   |
| delete_connection     | 删除连接配置   |
| list_connections      | 获取连接列表   |
| test_connection       | 测试连接       |
| connect_database      | 建立运行时连接 |
| disconnect_database   | 断开运行时连接 |
| get_connection_status | 查询连接状态   |

### 5.9 关键规则

- 连接配置与运行时连接分离。
- 一个 connection_id 对应一个独立运行时上下文。
- 多个连接可以同时存在。
- 连接删除不能删除查询历史。
- 连接删除不能删除 SQL 收藏。
- 不能将数据库密码保存在 SQLite。
- 不能因为切换前端标签而改变其他连接的运行状态。

## 6. 数据库资源管理模块

### 6.1 模块职责

数据库资源管理模块负责查询和展示 MySQL 数据库对象。

主要包含：

- 数据库列表。
- 表列表。
- 视图列表。
- 函数列表。
- 存储过程列表。

V1.0 优先实现数据库、表和视图。

### 6.2 资源数据模型

```
interface DatabaseInfo {
  name: string;
}

interface TableInfo {
  name: string;
  type: 'table' | 'view';
  comment?: string;
}
```

数据库对象名称不能假设唯一。

实际定位一个对象至少需要：

- connection_id。
- database_name。
- object_name。
- object_type。

### 6.3 核心接口

| 接口                 | 说明           |
| -------------------- | -------------- |
| list_databases       | 获取数据库列表 |
| list_tables          | 获取表列表     |
| list_views           | 获取视图列表   |
| refresh_explorer     | 刷新资源树     |
| get_current_database | 获取当前数据库 |

### 6.4 查询数据库列表

通过 MySQL Adapter 获取当前用户可见的数据库。

不应假设所有用户都拥有查看全部数据库的权限。

查询失败时返回明确的数据库权限错误。

### 6.5 查询表列表

需要返回：

- 表名。
- 对象类型。
- 表注释（能够获取时）。

表名需要保留原始大小写。

不能在前端擅自将表名转成小写。

### 6.6 懒加载

资源树建议使用懒加载。

例如：

1. 用户展开连接节点时加载数据库列表。
2. 用户展开数据库节点时加载表和视图列表。
3. 用户双击表节点时加载表数据。

不能在应用启动时一次性加载所有连接的全部数据库和全部表。

### 6.7 缓存策略

可以在前端缓存已加载的资源树数据。

缓存必须支持主动刷新。

切换连接后不能错误复用其他连接的数据。

资源树缓存的 key 应当包含：

```
connection_id
database_name
object_type
```

## 7. SQL 执行模块

### 7.1 模块职责

QueryService 负责 SQL 执行的完整业务流程。

包括：

- 接收执行请求。
- 验证执行上下文。
- 创建执行任务。
- 调用数据库适配器。
- 获取查询结果。
- 转换结果数据。
- 更新任务状态。
- 保存查询历史。
- 通知前端。

### 7.2 执行请求

```
interface ExecuteSqlRequest {
  connectionId: string;
  databaseName?: string;
  sql: string;

  executionMode:
    | 'current'
    | 'selected'
    | 'all';

  options?: {
    maxRows?: number;
    timeoutMs?: number;
  };
}
```

执行模式的含义：

| 模式     | 说明                       |
| -------- | -------------------------- |
| current  | 执行当前 SQL 语句          |
| selected | 执行用户选中的 SQL         |
| all      | 执行当前编辑器中的全部 SQL |

注意：

`current` 和 `selected` 的实际 SQL 内容应由前端编辑器或 SQL 解析层确定，后端仍需要验证 SQL 不为空。

后端不应假设自己能够准确识别所有 SQL 方言中的语句边界。

### 7.3 执行结果模型

```
interface QueryExecutionResult {
  taskId: string;
  status: QueryTaskStatus;

  resultSets: QueryResultSet[];

  affectedRows?: number;
  lastInsertId?: string;

  executionTimeMs: number;
  error?: QueryError;
}

interface QueryResultSet {
  columns: QueryColumn[];
  rows: DatabaseValue[];
  rowCount: number;
  truncated: boolean;
}

interface QueryColumn {
  name: string;
  typeName?: string;
  nullable?: boolean;
}
```

实际传输时，`rows` 应当采用二维数组形式：

```
interface QueryResultSet {
  columns: QueryColumn[];
  rows: DatabaseValue[][];
  rowCount: number;
  truncated: boolean;
}
```

### 7.4 执行流程

```
前端提交 SQL
      |
      ▼
QueryService
      |
      ├── 验证 connection_id
      ├── 验证连接状态
      ├── 验证 database_name
      ├── 验证 SQL 内容
      └── 创建 task_id
              |
              ▼
          TaskManager
              |
              ▼
          后台执行任务
              |
              ▼
          MySQL Adapter
              |
              ▼
          执行 SQL
              |
       ┌──────┴──────┐
       ▼             ▼
    查询结果       执行错误
       |             |
       └──────┬──────┘
              ▼
          更新任务状态
              |
       ┌──────┴──────┐
       ▼             ▼
    保存结果       保存错误
       |             |
       └──────┬──────┘
              ▼
          保存查询历史
              |
              ▼
          通知前端
```

### 7.5 多语句执行

V1.0 需要明确多语句执行策略。

建议默认：

- 当前语句执行：只执行当前识别出的语句。
- 选中 SQL 执行：执行选中内容。
- 全部执行：按照 SQL 语句顺序执行。

需要注意：

不同 MySQL 驱动对多语句执行的支持存在差异。

如果驱动不支持直接执行多语句，应由 SQL 解析层进行安全拆分，并按顺序执行。

不能简单使用分号拆分 SQL，因为分号可能出现在字符串、注释、存储过程等内容中。

V1.0 可以先明确支持普通 SQL 语句的执行，复杂存储过程和特殊多语句场景可以根据驱动能力逐步完善。

### 7.6 事务策略

需要区分：

- 用户显式执行 BEGIN、COMMIT、ROLLBACK。
- 应用主动开启事务。
- 数据修改页面内部使用的事务。

V1.0 不应擅自将所有 SQL 都包装进事务。

如果使用连接池，需要特别注意事务上下文必须绑定同一个物理数据库连接，不能在事务开始后随意切换连接池连接。

### 7.7 结果行数限制

默认结果展示上限建议为 10000 行。

具体策略：

- 仅针对返回记录集的查询。
- 不修改用户原始 SQL。
- 不自动为所有 SQL 添加 LIMIT。
- 超出限制后标记结果已截断。
- 提供明确提示。
- 后续可以提供专门的分页查询模式。

对于普通 SQL 执行，不能仅凭前端展示上限推断数据库只执行了前 10000 行。

### 7.8 错误处理

需要处理：

- 数据库连接不存在。
- 数据库连接断开。
- SQL 语法错误。
- 数据库权限不足。
- 查询超时。
- 结果转换失败。
- 查询取消。
- 驱动内部异常。

错误信息应尽量保留数据库原始错误内容，但不能泄露密码和敏感连接信息。

## 8. SQL 任务管理模块

### 8.1 模块职责

TaskManager 负责所有后台任务的生命周期。

V1.0 至少管理：

- SQL 执行任务。
- 数据导出任务。

后续可以扩展其他后台任务。

### 8.2 任务模型

```
type TaskType =
  | 'query'
  | 'export';

type QueryTaskStatus =
  | 'pending'
  | 'running'
  | 'success'
  | 'failed'
  | 'cancelled';

interface TaskInfo {
  taskId: string;
  taskType: TaskType;
  connectionId?: string;
  status: QueryTaskStatus;

  progress?: number;
  message?: string;

  createdAt: number;
  startedAt?: number;
  finishedAt?: number;
}
```

### 8.3 任务生命周期

```
创建任务
   |
   ▼
pending
   |
   ▼
running
   |
   ├── success
   ├── failed
   └── cancelled
```

终态任务不能随意回退到 running。

### 8.4 任务管理接口

| 接口         | 说明         |
| ------------ | ------------ |
| create_task  | 创建任务     |
| get_task     | 获取任务信息 |
| list_tasks   | 查询任务列表 |
| cancel_task  | 取消任务     |
| cleanup_task | 清理任务资源 |

### 8.5 任务取消

取消任务需要考虑：

1. 任务是否已经开始。
2. 任务是否支持真正取消。
3. 是否正在执行数据库操作。
4. 是否正在写入文件。
5. 是否需要回滚事务。
6. 是否需要清理临时资源。

不能仅将任务状态修改为 cancelled，就认为任务已经停止。

### 8.6 任务与连接关系

SQL 任务必须关联 connection_id。

连接断开时：

- 禁止提交新的关联任务。
- 找出正在执行的关联任务。
- 尝试取消或等待任务。
- 释放任务占用的资源。
- 更新任务状态。

不同连接的任务必须相互隔离。

### 8.7 任务事件

建议通过 Tauri Event 通知前端。

事件名称建议：

```
task:created
task:started
task:progress
task:completed
task:failed
task:cancelled
```

事件内容必须包含 task_id。

前端根据 task_id 更新对应标签页或任务面板。

## 9. 表数据浏览模块

### 9.1 模块职责

DataBrowserService 负责 MySQL 表数据浏览和编辑。

包括：

- 查询表数据。
- 分页。
- 排序。
- 筛选。
- 新增记录。
- 修改记录。
- 删除记录。
- 保存修改。
- 刷新数据。

### 9.2 表定位参数

```
interface TableRef {
  connectionId: string;
  databaseName: string;
  tableName: string;
}
```

所有表操作必须使用完整定位信息。

不能只通过 tableName 确定操作对象。

### 9.3 查询表数据

接口：

```
interface QueryTableDataRequest {
  table: TableRef;

  page: number;
  pageSize: number;

  filters?: FilterCondition[];
  sorts?: SortCondition[];
}
```

返回：

```
interface QueryTableDataResponse {
  columns: QueryColumn[];
  rows: DatabaseValue[][];

  page: number;
  pageSize: number;

  total?: number;
  hasMore: boolean;
}
```

### 9.4 分页实现

V1.0 建议采用 LIMIT / OFFSET。

例如：

```
SELECT *
FROM users
LIMIT 100 OFFSET 0;
```

注意：

- page 从 1 开始。
- OFFSET = (page - 1) × pageSize。
- pageSize 由后端限制。
- 排序应尽可能包含稳定的唯一键，避免翻页时出现重复或遗漏。
- 大型表深分页性能问题可以在后续版本优化。

精确 total 可以按需查询，不应无条件执行高成本 COUNT。

### 9.5 筛选模型

```
interface FilterCondition {
  field: string;

  operator:
    | 'eq'
    | 'ne'
    | 'gt'
    | 'gte'
    | 'lt'
    | 'lte'
    | 'contains'
    | 'not_contains'
    | 'is_null'
    | 'is_not_null';

  value?: DatabaseValue;
}
```

筛选规则：

- 字段名必须经过数据库元信息校验。
- 操作符必须使用白名单。
- 值使用参数化查询。
- NULL 判断使用 IS NULL / IS NOT NULL。
- LIKE 查询需要正确处理通配符。
- 不允许前端传入任意 SQL 片段作为筛选条件。

### 9.6 排序模型

```
interface SortCondition {
  field: string;
  direction: 'asc' | 'desc';
}
```

排序规则：

- 字段名必须校验。
- 排序方向必须使用白名单。
- 多字段排序按指定顺序生效。
- 不能直接将前端字符串拼接到 ORDER BY。

### 9.7 新增记录

接口：

```
interface InsertRowRequest {
  table: TableRef;
  values: Record<string, DatabaseValue>;
}
```

处理流程：

1. 校验表定位。
2. 获取表结构。
3. 校验字段。
4. 处理默认值和自增字段。
5. 构造参数化 INSERT。
6. 执行插入。
7. 返回影响行数和自增 ID。
8. 刷新当前数据。

不能强制要求用户填写所有字段。

### 9.8 修改记录

接口：

```
interface UpdateRowRequest {
  table: TableRef;

  originalValues: Record<string, DatabaseValue>;
  changes: Record<string, DatabaseValue>;
}
```

实际更新优先使用主键或唯一键定位记录。

推荐定位顺序：

1. 主键。
2. 能够唯一确定记录的唯一索引。
3. 无可靠唯一标识时，不默认允许普通编辑保存。

如果没有主键或唯一键，不能简单使用前端行号作为 WHERE 条件。

也不能仅凭旧字段值拼接 WHERE 就假设一定只会更新一行。

对于无法可靠定位的表，可以提供只读浏览，或者要求用户通过明确 SQL 进行修改。

更新完成后需要检查影响行数。

如果影响行数为 0，提示数据可能已经发生变化。

如果影响行数大于 1，而预期只修改一条记录，应当视为异常并处理。

### 9.9 删除记录

接口：

```
interface DeleteRowRequest {
  table: TableRef;
  primaryKeyValues: Record<string, DatabaseValue>;
}
```

对于存在主键的表，优先根据主键删除。

删除前需要二次确认。

对于没有主键或唯一键的表，默认不提供普通行删除操作。

不能通过数组下标、页面行号等前端信息直接定位数据库记录。

### 9.10 数据编辑状态

建议前端维护：

```
type RowEditStatus =
  | 'normal'
  | 'added'
  | 'modified'
  | 'deleted';
```

编辑状态只用于界面管理。

真正保存时仍需要后端进行完整校验。

## 11. 查询历史模块

### 11.1 模块职责

HistoryService 负责保存和查询用户 SQL 执行历史。

历史数据保存在本地 SQLite。

### 11.2 历史记录模型

```
interface QueryHistory {
  id: string;

  connectionId: string;
  connectionName: string;

  databaseName?: string;
  sql: string;

  status: QueryTaskStatus;

  startedAt: number;
  finishedAt?: number;

  executionTimeMs?: number;
  affectedRows?: number;

  errorMessage?: string;
}
```

### 11.3 历史保存时机

SQL 任务创建后：

1. 创建历史记录。
2. 保存初始状态 pending。
3. 任务开始时更新 running。
4. 执行结束时更新最终状态。
5. 保存执行耗时和结果摘要。
6. 保存错误信息（如果有）。

不能只在 SQL 执行成功时才保存历史。

失败和取消的 SQL 也应该保留记录。

### 11.4 历史查询

支持：

- 按连接筛选。
- 按数据库筛选。
- 按执行状态筛选。
- 按时间筛选。
- 按 SQL 内容搜索。
- 分页查询。

### 11.5 历史操作

支持：

- 查看 SQL。
- 复制 SQL。
- 重新打开 SQL。
- 删除历史记录。
- 清空历史记录。

重新执行历史 SQL 时，必须重新确认连接和数据库上下文。

不能因为历史记录中保存了 connection_id，就假设该连接仍然存在或仍然可用。

### 11.6 历史保留策略

V1.0 可以先不自动清理历史记录。

后续提供：

- 最大保存条数。
- 按时间清理。
- 手动清理。

SQL 内容可能包含业务数据和敏感信息，后续可以增加历史记录隐私设置。

## 15. 统一接口规范

### 15.1 命名规范

Rust Command 建议使用 snake_case。

TypeScript 方法使用 camelCase。

例如：

```
Rust Command:
    connect_database

Frontend:
    connectDatabase
```

### 15.2 请求规范

所有请求需要明确：

- 参数名称。
- 参数类型。
- 是否必填。
- 参数校验规则。
- 错误返回方式。

### 15.3 响应规范

建议统一返回结构：

```
interface ApiResult<T> {
  success: boolean;
  data?: T;
  error?: {
    code: string;
    message: string;
  };
}
```

说明：

Tauri Command 可以直接使用 `Result<T, E>` 返回。

以上 ApiResult 主要用于统一业务响应约定，不要求所有 Command 都必须重复包装一层。

错误码用于程序判断，错误信息用于用户阅读。

## 17. 并发与资源管理

### 17.1 多连接并发

不同 connection_id 的数据库操作应当能够并行执行。

一个连接的查询不应该阻塞其他连接。

### 17.2 同一连接并发

同一个连接可能同时存在多个工作区标签。

需要根据底层驱动能力决定是否允许并行执行。

建议：

- 普通独立查询可以并发。
- 同一事务中的操作必须绑定同一物理连接。
- 同一连接的数据库切换操作需要避免影响其他查询。
- 不允许通过全局 currentDatabase 变量管理所有标签的数据库上下文。

### 17.3 连接池

如果采用连接池：

- 每个数据库连接配置拥有独立连接池。
- 连接池大小可使用合理默认值。
- 连接池需要有连接超时和空闲连接策略。
- 事务不能随意跨物理连接。
- 连接断开时应正确关闭连接池。

具体池大小需要结合实际驱动和用户机器资源测试，不应固定为不合理的大数值。

### 17.4 任务资源清理

每个任务完成后，需要释放：

- 数据库游标或结果流。
- 临时文件。
- 内存缓冲区。
- 事件订阅相关资源。
- 任务状态对象。

任务历史可以持久化，但运行时任务资源不应永久保留。

## 18. 安全与数据完整性

### 18.1 SQL 安全

- 参数化查询。
- 动态字段名白名单校验。
- 动态表名校验和转义。
- 筛选条件不能直接执行任意 SQL。
- 排序方向必须使用白名单。
- 不能信任前端提供的数据库对象名称。

### 18.2 数据修改安全

- 删除需要确认。
- 更新需要可靠定位条件。
- 影响行数必须检查。
- 无唯一标识的表默认只读。
- 保存失败不能清空用户编辑内容。
- 发生数据冲突时需要提示用户重新加载。

### 18.3 本地安全

- 密码保存在系统凭据服务。
- SQLite 不保存明文密码。
- 日志不记录敏感凭据。
- 导出文件路径由用户明确选择。
- 不在前端持久化敏感信息。

## 21. AI 开发约束

后续 AI 编码必须遵守以下要求：

1. 严格按照模块职责实现。
2. 不允许把所有逻辑集中在 Command 层。
3. 不允许前端直接连接 MySQL。
4. 不允许在前端保存明文数据库密码。
5. 不允许使用全局单连接变量代替多连接管理。
6. 不允许通过当前选中标签推断后端连接目标。
7. SQL 执行必须关联独立 task_id。
8. 后台任务必须具有明确生命周期。
9. 不能将任务状态取消等同于数据库服务器已经停止执行。
10. 所有数据浏览操作必须包含完整表定位信息。
11. 所有动态 SQL 标识符必须校验和转义。
12. 所有筛选值必须参数化。
13. 无主键或唯一键的表不能默认允许危险编辑。
14. 所有数据库返回值必须正确处理 NULL 和精度。
15. 不允许为了简单而将所有数据库值转换成普通字符串。
16. 大数据量查询和导出必须考虑内存限制。
17. 不能为尚未实现的 Redis 和 PostgreSQL 编写大量无用代码。
18. 所有接口必须有类型定义和错误处理。
19. 每完成一个模块都应当编写对应测试。
20. 不得擅自改变已经确定的产品需求和技术架构。

## 22. 最终设计原则

DataDock V1.0 的核心模块需要围绕 MySQL 数据库客户端体验构建。

重点不是追求模块数量，而是保证以下能力可靠：

- 数据库连接可靠。
- 多连接管理正确。
- SQL 执行稳定。
- 查询结果准确。
- 数据修改安全。
- 数据结构展示正确。
- 查询历史可追溯。
- 大数据量操作不会轻易耗尽资源。

模块设计必须保持简单、清晰和可扩展。

**当前优先保证 MySQL 的完整使用体验，再考虑增加 Redis 和 PostgreSQL，而不是为了多数据源支持提前引入过度复杂的抽象。**
