# DataDock 项目目录结构与代码规范

> 文档版本：V1.0
> 文档状态：开发规范
> 适用版本：V1.0（MySQL）
> 所属项目：DataDock

## 1. 文档说明

### 1.1 编写目的

本文档用于统一 DataDock 项目的代码组织方式和开发规范。

主要解决：

1. 项目整体目录如何划分？
2. Vue 前端代码如何组织？
3. Rust 后端代码如何分层？
4. Command、Service、Repository、Adapter 分别放在哪里？
5. 公共组件和业务组件如何区分？
6. TypeScript 和 Rust 应遵循什么代码规范？
7. 新增功能时应该如何组织文件？
8. AI 编码时如何避免代码混乱和重复实现？

### 1.2 适用范围

本文档适用于：

- Tauri 桌面应用。
- Vue 3 前端。
- TypeScript。
- Rust 后端。
- SQLite 本地数据库。
- MySQL 数据源适配器。

### 1.3 基本原则

- 按业务模块组织代码。
- 按技术职责划分层级。
- 避免单文件承载过多业务。
- 公共能力统一封装。
- 前后端职责明确。
- 不允许跨模块随意访问内部实现。
- 不为了抽象而抽象。
- 不提前创建大量暂时用不到的模块。
- 项目结构允许随着实际开发调整，但必须保持职责清晰。

## 3. Vue 前端目录设计

### 3.1 src/api

负责所有 Tauri Command 和 Event 通信。

```
src/api/
├── index.ts
├── connection.ts
├── explorer.ts
├── query.ts
├── data-browser.ts
├── schema.ts
├── history.ts
├── favorite.ts
├── export.ts
├── settings.ts
├── workspace.ts
└── events.ts
```

职责：

| 文件            | 说明               |
| --------------- | ------------------ |
| index.ts        | 统一 IPC 调用封装  |
| connection.ts   | 连接管理接口       |
| explorer.ts     | 数据库资源接口     |
| query.ts        | SQL 执行和结果接口 |
| data-browser.ts | 表数据操作接口     |
| schema.ts       | 表结构接口         |
| history.ts      | 查询历史接口       |
| favorite.ts     | SQL 收藏接口       |
| export.ts       | 数据导出接口       |
| settings.ts     | 应用设置接口       |
| workspace.ts    | 工作区接口         |
| events.ts       | 后端事件订阅       |

规范：

- API 文件只负责通信。
- 不允许在 API 文件中实现复杂业务逻辑。
- 不允许 API 直接操作 Vue 组件。
- 不允许多个模块重复封装 invoke。
- API 请求和响应类型统一放在 types 目录。

### 3.2 src/assets

存放静态资源。

```
src/assets/
├── images/
├── icons/
└── fonts/
```

存放：

- 应用内部图片。
- 自定义 SVG 图标。
- 字体文件。
- 其他静态资源。

优先使用统一图标库，只有必要时才添加自定义图标。

存放可复用 UI 组件。

│   ├── AppStatusBar.vue
│   └── WorkspaceContainer.vue
│
├── database/
│   ├── ConnectionTree.vue
│   ├── DatabaseTreeNode.vue
│   ├── TableTreeNode.vue
│   ├── ConnectionStatus.vue
│   └── ConnectionDialog.vue
│
├── editor/
│   ├── SqlEditor.vue
│   ├── EditorToolbar.vue

│
├── result/

组件划分原则：

**common**

不依赖具体数据库业务的通用组件。

**layout**

负责整体页面布局。

**database**

负责数据库连接树和连接相关 UI。

**editor**

负责 SQL 编辑器。

**result**

负责查询结果展示。

**data-browser**

负责表数据浏览和编辑。

组件应当尽可能通过 props 和 emits 进行通信，不应随意直接访问其他组件内部状态。

### 3.4 src/composables

存放 Vue Composition API 逻辑。

```
src/composables/
├── useConnection.ts
├── useSqlEditor.ts
├── useQueryTask.ts
├── useQueryResult.ts
├── useDataBrowser.ts
├── useTableSchema.ts
├── useWorkspace.ts
└── useTheme.ts
```

职责：

- 封装可复用的交互逻辑。
- 组合 Store 和 API。
- 处理页面级业务状态。
- 统一处理加载状态和错误提示。

例如：

`useQueryTask.ts` 负责 SQL 任务提交、状态监听和取消操作。

不要把所有业务都写入 composable。

### 3.5 src/constants

存放前端常量。

```
src/constants/
├── app.ts
├── connection.ts
├── editor.ts
├── query.ts
└── theme.ts
```

例如：

```
export const DEFAULT_PAGE_SIZE = 100;

export const PAGE_SIZE_OPTIONS = [
  50,
  100,
  200,
  500,
];

export const DEFAULT_MAX_RESULT_ROWS = 10000;
```

常量必须集中维护，避免多个页面出现相同配置的不同版本。

### 3.6 src/layouts

存放页面整体布局。

```
src/layouts/
└── MainLayout.vue
```

MainLayout 负责：

- 顶部菜单。
- 工具栏。
- 左侧资源树。
- 中央工作区。
- 底部结果区。
- 状态栏。

主界面应当以 Navicat 式数据库客户端布局为基础。

不应改成 VS Code 风格的左侧文件资源管理器加右侧代码编辑器布局。

### 3.7 src/router

存放路由配置。

```
src/router/
└── index.ts
```

DataDock 是桌面应用，路由结构不需要过度复杂。

建议保留：

- 主工作区。
- 设置页面。
- 关于页面。

主工作区内部的 SQL 编辑器和表数据页面可以使用工作区标签管理，不一定全部使用 Vue Router 路由。

### 3.8 src/stores

存放 Pinia Store。

```
src/stores/
├── app.ts
├── connection.ts
├── explorer.ts
├── workspace.ts
├── query.ts
├── task.ts
├── settings.ts
└── ui.ts
```

职责：

| Store      | 负责内容           |
| ---------- | ------------------ |
| app        | 应用运行状态       |
| connection | 连接列表和连接状态 |
| explorer   | 数据库资源树       |
| workspace  | 工作区标签         |
| query      | SQL 查询状态       |
| task       | 后台任务状态       |
| settings   | 应用设置           |
| ui         | 全局 UI 状态       |

Store 规范：

- 不直接操作数据库。
- 通过 API 调用后端。
- 不保存数据库明文密码。
- 不将所有页面状态集中到一个 Store。
- 临时输入状态优先留在组件内部。
- 只有多个组件需要共享的状态才放入 Store。

### 3.9 src/styles

存放全局样式。

```
src/styles/
├── reset.css
├── variables.css
├── themes.css
├── typography.css
├── layout.css
└── global.css
```

建议通过 CSS Variables 管理主题。

示例：

```
:root {
  --app-bg: #f5f6f8;
  --panel-bg: #ffffff;

  --text-primary: #202124;
  --text-secondary: #6b7280;

  --border-color: #e5e7eb;

  --primary-color: #3b82f6;

  --radius-sm: 6px;
  --radius-md: 10px;
  --radius-lg: 14px;
}
```

暗色主题使用单独的变量覆盖，不要为每个组件单独写一套主题判断。

### 3.10 src/types

存放前端类型定义。

```
src/types/
├── api.ts
├── connection.ts
├── database.ts
├── query.ts
├── task.ts
├── history.ts
├── favorite.ts
├── settings.ts
└── workspace.ts
```

要求：

- 一个业务领域的类型尽量集中管理。
- 避免在多个组件重复定义相同接口。
- API 请求和响应类型必须与 Rust 后端一致。
- 不使用大量 any 逃避类型检查。
- 类型调整时同步检查调用方。

### 3.11 src/utils

存放纯工具函数。

```
src/utils/
├── date.ts
├── format.ts
├── sql.ts
├── database-value.ts
├── validation.ts
└── clipboard.ts
```

例如：

- 时间格式化。
- 数据库值格式化。
- SQL 文本处理。
- 参数校验。
- 剪贴板操作。

工具函数尽量保持无副作用。

如果一个工具需要调用后端，应当放入 API 或 composable，不应伪装成普通纯函数。

### 3.12 src/views

存放主要页面。

```
src/views/
├── workspace/
│   └── WorkspaceView.vue
│
├── settings/
│   ├── SettingsView.vue
│   ├── GeneralSettings.vue
│   ├── AppearanceSettings.vue
│   ├── EditorSettings.vue
│   └── QuerySettings.vue
│
└── about/
    └── AboutView.vue
```

说明：

SQL 编辑器、表数据浏览器等主要工作区功能，可以由 WorkspaceView 通过组件和标签状态进行组合，不要求每个功能都单独创建一个路由页面。

### 4.2 commands

Command 层负责 Tauri IPC 入口。

例如：

```
commands/connection.rs
```

包含：

- create_connection。
- update_connection。
- delete_connection。
- list_connections。
- test_connection。
- connect_database。
- disconnect_database。
- get_connection_status。

规范：

- Command 不直接操作 SQLite。
- Command 不直接执行 MySQL SQL。
- Command 不负责连接池管理。
- Command 只负责参数接收、调用 Service 和返回结果。
- Command 不能承载大量业务判断。

### 4.3 services

Service 层负责业务逻辑。

例如：

```
connection_service.rs
```

负责：

- 创建连接业务。
- 更新连接业务。
- 删除连接业务。
- 测试连接。
- 建立连接。
- 断开连接。

Service 可以组合调用：

- Repository。
- ConnectionManager。
- DataSourceRegistry。
- CredentialService。

Service 不应依赖前端组件或 Vue 状态。

### 4.4 repositories

Repository 层负责本地数据持久化。

主要操作 SQLite。

例如：

```
connection_repository.rs
```

负责：

- 保存连接配置。
- 更新连接配置。
- 删除连接配置。
- 查询连接配置。
- 查询连接详情。

Repository 不负责连接远程 MySQL。

### 4.5 adapters

Adapter 层负责具体数据源的实现。

V1.0：

```
adapters/
└── mysql/
```

MySQL Adapter 内部进一步拆分：

| 文件               | 职责                 |
| ------------------ | -------------------- |
| adapter.rs         | 适配器注册和入口     |
| connection.rs      | MySQL 连接建立与释放 |
| query.rs           | SQL 执行             |
| explorer.rs        | 数据库资源查询       |
| data_browser.rs    | 表数据查询与修改     |
| schema.rs          | 表结构查询           |
| value_converter.rs | 数据库值转换         |

后续增加 Redis 时：

```
adapters/
├── mysql/
└── redis/
```

不能将 Redis 的数据结构强行转换成 MySQL 的表、字段、行模型。

### 4.6 database

负责本地 SQLite。

包含：

- 数据库初始化。
- 数据库连接管理。
- Migration。
- 本地数据库基础配置。

SQLite 和远程 MySQL 是两个不同的数据存储对象，不能混淆。

### 4.7 models

存放 Rust 领域模型和 IPC 数据模型。

建议根据实际需要区分：

- 请求模型。
- 响应模型。
- 领域模型。
- 数据库持久化模型。

不要为了减少文件数量，把所有模型写在一个巨大的 common.rs 中。

### 4.8 tasks

负责后台任务实现。

例如：

- QueryTask。
- ExportTask。
- TaskManager。

任务需要具有独立 task_id 和明确生命周期。

### 4.9 core

负责核心运行时基础能力：

- ConnectionManager。
- DataSourceRegistry。
- Runtime 初始化。

这里不放具体业务页面逻辑。

### 4.10 state.rs

负责应用全局状态定义。

例如：

```
pub struct AppState {
    pub connection_service: Arc<ConnectionService>,
    pub query_service: Arc<QueryService>,
    pub history_service: Arc<HistoryService>,
    pub task_manager: Arc<TaskManager>,
}
```

这是结构示意。

实际状态对象需要根据模块依赖和初始化顺序组织，避免循环依赖。

### 4.11 errors

统一定义错误。

例如：

```
pub struct AppError {
    pub code: String,
    pub message: String,
}
```

实际项目可以进一步封装错误枚举和底层错误转换。

不能让各个模块随意返回完全不同格式的错误。

### 4.12 events

统一管理 Tauri Event 名称和事件结构。

避免在业务代码中到处直接填写字符串事件名称。

## 5. 前后端模块对应关系

建议保持以下映射：

| 业务模块 | Vue 前端                                | Rust 后端                                                    |
| -------- | --------------------------------------- | ------------------------------------------------------------ |
| 连接管理 | api/connection.ts、stores/connection.ts | commands/connection.rs、services/connection_service.rs       |
| 资源树   | api/explorer.ts、stores/explorer.ts     | commands/explorer.rs、services/explorer_service.rs           |
| SQL 执行 | api/query.ts、stores/query.ts           | commands/query.rs、services/query_service.rs                 |
| 任务管理 | api/events.ts、stores/task.ts           | commands/task.rs、tasks/                                     |
| 数据浏览 | api/data-browser.ts                     | commands/data_browser.rs、services/data_browser_service.rs   |
| 表结构   | api/schema.ts                           | commands/schema.rs、services/schema_service.rs               |
| 查询历史 | api/history.ts                          | commands/history.rs、services/history_service.rs、repositories/history_repository.rs |
| SQL 收藏 | api/favorite.ts                         | commands/favorite.rs、services/favorite_service.rs           |
| 数据导出 | api/export.ts                           | commands/export.rs、services/export_service.rs               |
| 应用设置 | api/settings.ts、stores/settings.ts     | commands/settings.rs、services/settings_service.rs           |

## 7. 前端代码规范

### 7.1 Vue 组件规范

建议使用 Vue 3 Composition API 和 `<script setup>`。

示例：

```
<script setup lang="ts">
import { ref } from 'vue';

const loading = ref(false);

async function handleRefresh() {
  loading.value = true;

  try {
    // 调用业务方法
  } finally {
    loading.value = false;
  }
}
</script>

<template>
  <div class="connection-panel">
    <!-- 页面内容 -->
  </div>
</template>

<style scoped>
.connection-panel {
  min-width: 0;
}
</style>
```

要求：

- 使用 Composition API。
- 优先使用 `<script setup>`。
- 组件必须有明确职责。
- 不在模板中编写复杂业务表达式。
- 不在组件中重复实现公共 API 调用逻辑。
- 不允许组件直接访问 Rust 内部实现。

### 7.2 组件通信

优先使用：

- props。
- emits。
- Pinia。
- composables。

不建议：

- 大量跨层级组件直接互相调用。
- 通过 DOM 查找其他组件。
- 通过全局变量保存业务状态。
- 使用大量事件总线传递核心业务数据。

### 7.3 Store 规范

Store 只管理需要共享的状态。

例如：

连接 Store：

```
interface ConnectionState {
  connections: ConnectionInfo[];
  runtimeStatus: Record<string, ConnectionStatus>;
  activeConnectionId?: string;
}
```

不应该把连接密码放进 Store。

### 7.4 异步操作

所有异步调用必须处理错误。

建议：

```
async function refreshConnections() {
  loading.value = true;

  try {
    connections.value = await listConnections();
  } catch (error) {
    // 统一错误处理
  } finally {
    loading.value = false;
  }
}
```

避免未处理的 Promise 错误。

### 7.5 CSS 规范

- 优先使用 CSS Variables。
- 组件样式尽量局部化。
- 避免全局污染。
- 避免大量使用 !important。
- 不允许每个组件独立定义一套颜色。
- 主题通过统一变量管理。
- 保持 Navicat 式桌面客户端的布局体验。

### 7.6 UI 实现约束

- 不随意改变已经确定的主界面布局。
- 不将界面改成 VS Code 风格。
- 不使用传统后台管理系统模板。
- 玻璃拟态不能影响表格和 SQL 编辑器的可读性。
- 不过度使用阴影、渐变和动画。
- 交互反馈需要统一。

## 8. Rust 代码规范

### 8.1 模块职责

每个模块只负责自己的业务范围。

例如：

```
query_service.rs
```

负责 SQL 执行业务。

不应该直接承担：

- 连接配置 CRUD。
- 查询历史列表页面逻辑。
- 设置管理。
- 前端工作区状态。

### 8.2 错误处理

统一使用 Result 返回错误。

示例：

```
pub async fn execute_sql(
    request: ExecuteSqlRequest,
) -> Result<ExecuteSqlResponse, AppError> {
    // 业务逻辑
}
```

禁止：

- 大量使用 unwrap。
- 大量使用 expect。
- 忽略数据库错误。
- 将所有错误统一转成字符串。
- 使用 panic 代替正常错误处理。

测试代码中可以根据测试需要使用 expect。

### 8.3 异步规范

- 数据库 IO 使用异步方式。
- 文件导出考虑异步和分批写入。
- 不允许在异步运行时中执行长时间阻塞操作。
- 必要的阻塞操作使用合适的阻塞任务执行机制。
- 后台任务必须具备生命周期管理。

### 8.4 共享状态

多连接和任务管理需要明确所有权。

建议合理使用：

- Arc。
- Mutex。
- RwLock。
- Tokio 同步原语。

不能为了方便把所有状态都放进一个全局 Mutex。

锁的持有范围应当尽可能短。

执行 SQL 等长时间 IO 时，不应无必要地持有全局锁。

### 8.5 日志

统一使用结构化日志。

建议日志字段：

```
timestamp
level
module
connection_id
task_id
message
```

禁止记录：

- 数据库密码。
- 完整凭据。
- 用户敏感数据。
- 未经处理的敏感 SQL 参数。

## 9. 文件大小与模块拆分规范

### 9.1 不允许巨型文件

一个文件如果承担多个独立业务职责，应当拆分。

例如：

不建议：

```
mysql.rs
```

内部同时实现：

- 连接管理。
- 数据库列表。
- SQL 执行。
- 表数据查询。
- 表结构查询。
- 数据转换。

建议拆分成：

```
mysql/
├── connection.rs
├── explorer.rs
├── query.rs
├── data_browser.rs
├── schema.rs
└── value_converter.rs
```

### 9.2 组件拆分

组件拆分依据：

- 是否有独立业务职责。
- 是否存在重复 UI。
- 是否有独立状态。
- 是否需要单独测试。
- 是否有较复杂的交互。

不要求每一个小按钮都创建独立 Vue 文件。

### 9.3 公共代码

当多个模块出现真正相同的业务逻辑时，可以提取公共方法。

不要仅因为两个函数代码相似，就强行建立复杂抽象。

## 12. 新增功能开发流程

AI 或开发人员新增功能时，应遵循统一流程。

### 第一步：确认需求

明确：

- 功能属于哪个模块。
- 需要哪些输入。
- 返回什么结果。
- 是否涉及本地数据库。
- 是否涉及远程 MySQL。
- 是否需要新增 UI。
- 是否涉及任务或事件。

### 第二步：检查现有代码

先检查：

- 是否已有相同 API。
- 是否已有公共组件。
- 是否已有对应 Service。
- 是否已有对应 Repository。
- 是否已有可复用的模型。
- 是否已有错误码。

禁止未检查就重复创建一套实现。

### 第三步：定义数据结构

先定义：

- Request。
- Response。
- Model。
- Event（如果需要）。

同步更新前后端类型。

### 第四步：实现后端

按照：

```
Command
   |
   ▼
Service
   |
   ├── Repository
   |
   └── Adapter
```

实现业务。

### 第五步：实现前端 API

在对应 API 文件中增加调用方法。

### 第六步：实现 Store 或 Composable

根据业务状态需要决定是否增加 Store 或 composable。

不要所有功能都创建 Store。

### 第七步：实现 UI

使用现有组件和设计规范。

### 第八步：测试

完成：

- 参数测试。
- 正常流程测试。
- 异常流程测试。
- 交互测试。
- 数据完整性测试。

### 第九步：更新文档

如果新增或修改：

- Command。
- Event。
- 数据模型。
- SQLite 表。
- 模块职责。
- 技术依赖。

必须同步更新对应文档。

## 15. 最终目录设计原则

DataDock 的项目目录需要满足三个目标：

**第一，容易定位。**

看到连接管理问题，可以直接定位到 connection 模块。

看到 SQL 执行问题，可以直接定位到 query 模块。

**第二，职责清晰。**

Command、Service、Repository、Adapter 各自承担明确职责。

**第三，方便 AI 协作开发。**

AI 能够通过文件路径快速判断应该在哪个模块修改代码，而不是每次都需要阅读整个项目。

项目初期应当保持适度拆分。

不要为了追求架构完整性而提前创建大量暂时没有实际用途的文件。

随着 V1.0 功能逐步完成，再根据真实业务复杂度调整目录结构。

**最终目标是让 DataDock 保持结构清晰、代码可维护、模块可扩展，而不是让目录层级本身变得复杂。**
