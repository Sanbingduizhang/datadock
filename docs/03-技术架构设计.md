# DataDock 技术架构设计

> 文档版本：V1.0
> 文档状态：技术架构设计
> 适用版本：V1.0（MySQL）
> 所属项目：DataDock
> 桌面框架：Tauri

## 1. 技术架构概述

### 1.1 项目定位

DataDock 是一款基于 Tauri 开发的跨平台桌面数据库管理工具。

采用前后端分离的桌面应用架构：

- 前端负责 UI 展示、用户交互和工作区状态管理。
- Rust 后端负责数据库连接、SQL 执行、数据查询和本地数据持久化。
- SQLite 负责保存应用本地数据。
- 操作系统凭据管理机制负责保存数据库连接密码。
- 数据库驱动负责与远程 MySQL 数据库通信。

整体采用模块化架构，后续通过数据源适配器扩展 Redis、PostgreSQL 等数据源。

### 1.2 核心设计目标

1. 前后端职责明确。
2. 数据库连接相互隔离。
3. SQL 执行不阻塞 UI。
4. 支持多个数据库连接同时工作。
5. 数据源适配器可扩展。
6. 本地配置和查询历史可靠保存。
7. 敏感凭据安全存储。
8. 便于 AI 分模块开发和维护。
9. 不依赖官方云端服务。
10. 保留后续扩展能力，避免 V1.0 过度设计。

## 2. 技术选型

### 2.1 技术栈

| 层级       | 技术                       | 用途                 | 选型状态 |
| ---------- | -------------------------- | -------------------- | -------- |
| 桌面框架   | Tauri                      | 桌面应用容器         | 已确定   |
| 前端框架   | Vue 3                      | UI 开发              | 建议     |
| 开发语言   | TypeScript                 | 前端开发             | 建议     |
| 构建工具   | Vite                       | 前端构建             | 建议     |
| 后端语言   | Rust                       | 本地业务和数据库操作 | 建议     |
| 本地数据库 | SQLite                     | 保存应用配置和历史   | 已确定   |
| SQL 编辑器 | Monaco Editor              | SQL 编辑             | 建议     |
| 图标库     | Lucide                     | UI 图标              | 建议     |
| 状态管理   | Pinia                      | 前端状态管理         | 建议     |
| 数据库驱动 | SQLx 或其他成熟 MySQL 驱动 | MySQL 通信           | 待确认   |
| 异步运行时 | Tokio                      | 异步任务管理         | 建议     |
| 序列化     | Serde                      | 数据序列化           | 建议     |
| 日志       | tracing                    | Rust 日志            | 建议     |

说明：

以上技术选型以 Tauri + Rust 为整体实现方向。

具体依赖版本应当在正式创建项目时选择兼容的稳定版本，并锁定版本。

### 2.2 前端技术

建议使用：

- Vue 3。
- TypeScript。
- Composition API。
- Vite。
- Pinia。
- Vue Router。
- Monaco Editor。
- Lucide 图标库。

前端主要负责：

- 页面渲染。
- 用户交互。
- 工作区管理。
- 标签页管理。
- SQL 编辑器交互。
- 查询结果展示。
- 数据表格展示。
- 调用 Rust 后端接口。
- 接收后端任务状态和执行结果。

前端不直接连接远程数据库。

所有数据库操作统一通过 Tauri IPC 调用 Rust 后端。

### 2.3 Rust 后端

Rust 主要负责：

- 数据源连接管理。
- MySQL 数据库操作。
- SQL 执行。
- 表数据查询。
- 表结构查询。
- 本地 SQLite 操作。
- 凭据管理。
- 后台任务管理。
- 日志记录。
- 数据导出。

后端需要保持模块化，不应将所有业务逻辑堆积在 Tauri Command 中。

Tauri Command 只负责接收参数、调用 Service 和返回结果。

### 2.4 数据库驱动选型

V1.0 只实现 MySQL。

数据库驱动建议优先评估 SQLx。

SQLx 的优势：

- 支持异步操作。
- 支持 Tokio。
- 支持 MySQL。
- 支持连接池。
- 支持参数化查询。
- 可以与 Rust 的异步服务架构配合。

但 SQLx 并不意味着所有数据库客户端能力都可以直接使用其高级接口实现。

特别是需要执行任意用户 SQL、处理多个结果集、读取数据库元信息和控制查询任务时，需要实际验证驱动能力。

正式选型前需要重点验证：

1. 是否支持任意 SQL 执行。
2. 是否支持多条 SQL 的执行策略。
3. 是否支持多个结果集。
4. 是否能够获取列名和字段类型。
5. 是否能够处理 NULL。
6. 是否支持事务。
7. 是否能够取消正在执行的查询。
8. 是否能够安全管理多个连接。
9. 是否支持 MySQL 常见数据类型。
10. 是否适合数据库客户端的长期运行场景。

如果 SQLx 在特定能力上存在限制，可以针对性选择其他驱动或补充实现。

不要为了使用某个技术库而牺牲核心数据库客户端能力。

## 3. 前后端职责划分

### 3.1 前端职责

前端负责所有界面和交互相关工作。

主要模块：

| 模块       | 职责         |
| ---------- | ------------ |
| App        | 应用入口     |
| Layout     | 主界面布局   |
| Connection | 连接管理 UI  |
| Explorer   | 数据库资源树 |
| Workspace  | 多标签工作区 |
| Editor     | SQL 编辑器   |
| Result     | SQL 结果展示 |
| DataViewer | 表数据浏览   |
| Structure  | 表结构展示   |
| History    | 查询历史     |
| Favorites  | SQL 收藏     |
| Settings   | 应用设置     |

前端不应当：

- 直接保存数据库密码。
- 直接访问远程 MySQL。
- 在前端拼接数据库连接字符串。
- 自行处理底层数据库事务。
- 将大量数据库业务逻辑放在组件中。
- 将复杂 SQL 执行逻辑放在前端。

### 3.2 Rust 后端职责

后端负责实际数据操作。

主要模块：

| 模块        | 职责             |
| ----------- | ---------------- |
| Commands    | Tauri IPC 命令   |
| Connection  | 数据库连接管理   |
| DataSource  | 数据源适配器     |
| Query       | SQL 执行         |
| DataBrowser | 表数据查询和编辑 |
| Schema      | 表结构查询       |
| History     | 查询历史         |
| Favorites   | SQL 收藏         |
| Settings    | 应用设置         |
| Storage     | 本地 SQLite      |
| Credentials | 系统凭据管理     |
| Tasks       | 后台任务         |
| Export      | 数据导出         |

### 3.3 职责边界

前端可以决定展示什么，但不能决定数据库底层如何执行。

后端负责数据正确性、安全性和数据库操作。

例如：

用户点击表数据页面的下一页：

```
前端：
    用户点击下一页
        ↓
    调用 data_page_query
        ↓
后端：
    获取连接上下文
        ↓
    调用 MySQL Adapter
        ↓
    执行分页 SQL
        ↓
    返回字段和记录
        ↓
前端：
    更新表格
```

前端不应直接操作数据库连接对象。

## 4. 后端分层架构

建议 Rust 后端采用分层架构。

### 4.1 Command 层

负责 Tauri IPC 接口。

职责：

- 接收前端请求。
- 校验必要参数。
- 调用 Service。
- 转换返回数据。
- 返回统一错误结果。

Command 不应该包含复杂业务逻辑。

示例：

```
#[tauri::command]
async fn test_connection(
    request: TestConnectionRequest,
    state: tauri::State<'_, AppState>,
) -> Result<ConnectionTestResult, AppError> {
    state.connection_service
        .test_connection(request)
        .await
}
```

以上为结构示意，实际代码需要根据应用状态和依赖注入方式调整。

### 4.2 Service 层

负责业务逻辑。

例如：

ConnectionService：

- 创建连接。
- 编辑连接。
- 删除连接。
- 测试连接。
- 建立连接。
- 断开连接。

QueryService：

- 执行 SQL。
- 获取执行状态。
- 处理执行结果。
- 管理查询任务。
- 记录执行历史。

DataBrowserService：

- 查询表数据。
- 分页。
- 筛选。
- 排序。
- 新增数据。
- 修改数据。
- 删除数据。

SchemaService：

- 查询数据库列表。
- 查询表列表。
- 查询表结构。
- 查询索引。
- 获取建表 SQL。

### 4.3 Repository 层

负责本地 SQLite 数据读写。

例如：

- DataSourceRepository。
- QueryHistoryRepository。
- SqlFavoriteRepository。
- AppSettingsRepository。
- WorkspaceRepository。

Repository 不负责远程 MySQL 的 SQL 执行。

远程数据库操作由数据源适配器负责。

### 4.4 Adapter 层

负责不同数据源的具体实现。

例如：

- MySQL Adapter。
- Redis Adapter。
- PostgreSQL Adapter。

不同适配器负责各自的数据源协议、连接、查询和数据结构。

不要将所有数据源强行抽象成完全一致的数据库模型。

## 5. 数据源适配器架构

### 5.1 设计目标

DataDock 后续需要支持多种数据源。

因此 V1.0 就需要考虑数据源扩展问题。

但 V1.0 不需要提前实现 Redis 和 PostgreSQL。

只需要将 MySQL 的实现设计成独立适配器。

### 5.2 数据源接口

建议定义统一的基础能力接口。

示意：

```
#[async_trait::async_trait]
pub trait DataSourceAdapter: Send + Sync {
    async fn test_connection(
        &self,
        config: &ConnectionConfig,
    ) -> Result<ConnectionTestResult, AppError>;

    async fn connect(
        &self,
        config: &ConnectionConfig,
    ) -> Result<ConnectionHandle, AppError>;

    async fn disconnect(
        &self,
        connection_id: &str,
    ) -> Result<(), AppError>;

    async fn list_databases(
        &self,
        connection_id: &str,
    ) -> Result<Vec<DatabaseInfo>, AppError>;
}
```

以上只是接口设计示意。

实际实现时，需要根据各类数据源的能力拆分接口。

例如 SQL 数据库可以提供 SQL 执行和表结构查询能力，而 Redis 应当提供 Key、数据类型、过期时间和命令操作等能力。

不能要求 Redis 实现 MySQL 特有的表结构接口。

### 5.3 适配器注册

建议通过数据源类型注册对应适配器。

例如：

```
DataSourceRegistry
    ├── mysql  -> MySQLAdapter
    ├── redis  -> RedisAdapter
    └── postgres -> PostgreSQLAdapter
```

V1.0 只注册 MySQL。

未来增加 Redis 时，不应修改现有 MySQL 核心业务代码。

### 5.4 数据源类型定义

建议使用明确的数据源类型标识：

```
pub enum DataSourceType {
    MySQL,
    Redis,
    PostgreSQL,
}
```

持久化时使用稳定字符串：

```
mysql
redis
postgresql
```

不要直接将 Rust 枚举内部实现格式作为数据库持久化协议。

## 6. 数据库连接管理架构

### 6.1 连接管理目标

DataDock 允许用户同时配置和使用多个数据库连接。

连接管理需要解决：

- 多连接并存。
- 连接状态管理。
- 连接资源释放。
- 查询任务与连接关联。
- 连接断开后的任务处理。
- 连接配置与运行时连接分离。

### 6.2 连接信息分离

连接信息分为两部分：

**持久化配置**

保存到本地 SQLite：

- 连接 ID。
- 连接名称。
- 主机。
- 端口。
- 用户名。
- 默认数据库。
- 其他连接参数。
- 凭据引用。

**运行时连接**

保存在 Rust 后端内存：

- 连接对象或连接池。
- 连接状态。
- 当前数据库。
- 活动任务。
- 连接运行时信息。

密码不应该直接存储在 SQLite 中。

需要通过系统凭据管理机制获取密码，再建立远程连接。

### 6.3 连接管理器

建议提供 ConnectionManager。

职责：

- 管理运行时连接。
- 创建连接。
- 获取连接。
- 断开连接。
- 查询连接状态。
- 处理异常断开。
- 释放资源。

建议逻辑：

```
ConnectionManager
    |
    ├── Connection A
    │     ├── MySQL Pool
    │     ├── Connection State
    │     └── Active Tasks
    │
    ├── Connection B
    │     ├── MySQL Pool
    │     ├── Connection State
    │     └── Active Tasks
    │
    └── Connection C
          ├── MySQL Pool
          ├── Connection State
          └── Active Tasks
```

### 6.4 连接隔离

每个数据源连接必须有独立的运行时上下文。

不能因为用户切换了工作区标签，就错误地将 SQL 发往其他数据库。

每次 SQL 执行必须明确指定：

- connection_id。
- database_name。
- SQL 内容。
- 执行选项。

不能仅依赖前端当前选中的连接来推断后端执行目标。

### 6.5 连接生命周期

```
未连接
  |
  | 用户发起连接
  ▼
连接中
  |
  ├── 成功 ──> 已连接
  |
  └── 失败 ──> 连接失败

已连接
  |
  ├── 用户主动断开
  ├── 数据库连接异常
  └── 应用退出
        |
        ▼
     释放连接资源
```

连接断开时：

- 不允许继续提交新的数据库操作。
- 处理或取消关联的活动任务。
- 释放连接池或连接资源。
- 更新连接状态。
- 通知前端刷新连接状态。

具体取消行为需要结合数据库驱动能力实现。

## 7. SQL 执行架构

### 7.1 执行流程

SQL 执行统一由后端 QueryService 负责。

```
用户执行 SQL
      |
      ▼
前端校验执行上下文
      |
      ▼
调用 execute_sql
      |
      ▼
后端 QueryService
      |
      ├── 验证连接 ID
      ├── 验证数据库上下文
      ├── 创建任务 ID
      ├── 记录执行开始时间
      └── 提交异步任务
              |
              ▼
        MySQL Adapter
              |
              ▼
          执行 SQL
              |
       ┌──────┴──────┐
       ▼             ▼
    查询结果       执行错误
       |             |
       └──────┬──────┘
              ▼
         任务状态更新
              |
              ▼
         保存查询历史
              |
              ▼
         通知前端结果
```

### 7.2 SQL 执行上下文

每次执行必须包含：

```
interface ExecuteSqlRequest {
  connectionId: string;
  databaseName?: string;
  sql: string;
  executionMode: 'current' | 'selected' | 'all';
  options?: {
    maxRows?: number;
    timeoutMs?: number;
  };
}
```

以上为前端接口类型示意。

后端需要再次校验参数，不能信任前端传入的连接和执行选项。

### 7.3 执行任务 ID

每次 SQL 执行生成独立 task_id。

例如：

```
task_001
task_002
task_003
```

实际建议使用 UUID。

任务 ID 用于：

- 查询任务状态。
- 获取执行结果。
- 取消任务。
- 关联执行日志。
- 关联查询历史。

### 7.4 异步执行

SQL 执行不能阻塞 UI。

建议通过 Tokio 管理异步任务。

执行过程应当与 Tauri IPC 请求生命周期解耦。

对于耗时较长的 SQL，不建议一直占用一个前端 IPC 请求等待全部结果。

可以采用：

1. 前端提交执行请求。
2. 后端立即返回 task_id。
3. 后端在后台执行任务。
4. 后端通过事件通知任务状态。
5. 前端根据 task_id 获取结果。

也可以根据结果大小采用分批返回。

### 7.5 执行状态

建议定义：

```
type QueryTaskStatus =
  | 'pending'
  | 'running'
  | 'success'
  | 'failed'
  | 'cancelled';
```

状态含义：

| 状态      | 说明     |
| --------- | -------- |
| pending   | 等待执行 |
| running   | 正在执行 |
| success   | 执行成功 |
| failed    | 执行失败 |
| cancelled | 已取消   |

任务状态应当由后端统一维护。

### 7.6 查询结果限制

为了避免大型查询占用过多内存，建议提供默认结果行数限制。

例如默认最多返回 10000 行。

注意：

- 该限制是普通查询结果展示策略。
- 不能简单地给所有 SQL 自动添加 LIMIT。
- INSERT、UPDATE、DELETE、DDL 等语句不能套用查询结果限制。
- 不能随意修改用户原始 SQL 的语义。
- 对超出结果限制的情况需要明确提示。
- 后续可以支持用户调整默认值。

### 7.7 SQL 执行取消

提供停止执行功能。

需要区分：

- 用户取消请求。
- 后端停止等待。
- 数据库服务器实际停止执行。

这三者并不完全等价。

如果驱动不支持真正的查询取消，不能仅仅取消 Rust Future 就声称数据库执行已经停止。

必要时需要研究数据库驱动提供的取消机制，或者采用独立连接执行和中断方案。

## 8. 本地存储架构

### 8.1 本地 SQLite

DataDock 使用 SQLite 保存应用本地数据。

主要数据：

- 数据源配置。
- 查询历史。
- SQL 收藏。
- 应用设置。
- 工作区状态。

SQLite 只用于 DataDock 自身的数据存储，不用于替代用户远程 MySQL。

### 8.2 存储访问

所有 SQLite 读写统一通过 Repository 层。

业务 Service 不应该直接在多个地方编写重复的 SQL。

### 8.3 初始化流程

```
应用启动
   |
   ▼
获取应用数据目录
   |
   ▼
检查本地 SQLite 文件
   |
   ├── 不存在：创建数据库
   └── 已存在：打开数据库
   |
   ▼
执行数据库迁移
   |
   ▼
初始化 Repository
   |
   ▼
加载应用配置
   |
   ▼
恢复工作区状态
   |
   ▼
进入主界面
```

### 8.4 数据库迁移

建议使用成熟的 SQLite Migration 机制。

每次修改本地表结构时，需要增加对应迁移。

不能通过简单地判断某个字段是否存在来代替完整迁移管理。

具体采用 SQLx Migration 或其他方案，需要结合最终依赖确定。

## 9. 系统凭据管理

### 9.1 设计目标

数据库密码属于敏感信息。

不能以明文形式存入 SQLite。

建议使用系统原生凭据管理能力：

- macOS：Keychain。
- Windows：Windows Credential Manager 或等效安全凭据接口。
- Linux：Secret Service 等可用凭据服务。

具体跨平台库需要在依赖选型阶段验证。

### 9.2 凭据保存

连接配置中只保存凭据引用：

```
credential_key
```

实际密码保存在系统凭据管理服务中。

### 9.3 凭据生命周期

创建连接：

1. 保存密码到系统凭据管理。
2. 获取凭据引用。
3. 保存连接配置到 SQLite。

编辑连接：

1. 如果用户修改密码，更新系统凭据。
2. 如果用户没有修改密码，保留原凭据。
3. 更新其他连接配置。

删除连接：

1. 关闭运行时连接。
2. 删除系统凭据。
3. 删除本地连接配置。

### 9.4 异常处理

需要考虑：

- 系统凭据服务不可用。
- 凭据不存在。
- 用户删除系统凭据。
- 凭据读取失败。
- 应用重新启动后无法读取凭据。

不能因为密码读取失败就自动使用空密码连接数据库。

## 10. 事件通信架构

### 10.1 IPC 通信

前端与 Rust 后端通过 Tauri IPC 交互。

适合使用 Command 的场景：

- 创建连接。
- 测试连接。
- 查询数据库列表。
- 查询表结构。
- 查询表数据。
- 提交 SQL。
- 查询任务结果。
- 修改设置。

### 10.2 事件通信

适合使用 Tauri Event 的场景：

- SQL 执行状态变化。
- 查询任务进度。
- 连接状态变化。
- 长时间导出任务进度。
- 后台任务完成通知。

### 10.3 事件格式

建议统一事件结构。

例如：

```
interface AppEvent<T> {
  eventId: string;
  eventType: string;
  timestamp: number;
  payload: T;
}
```

SQL 任务事件：

```
interface QueryTaskEvent {
  taskId: string;
  connectionId: string;
  status: QueryTaskStatus;
  progress?: number;
  message?: string;
}
```

事件中的字段应当由后端产生或验证。

不能仅凭前端事件就认为任务执行成功。

### 10.4 事件订阅管理

前端需要统一管理事件监听器。

要求：

- 页面或组件销毁时解除监听。
- 避免重复订阅。
- 通过 task_id 区分任务。
- 通过 connection_id 区分连接。
- 不允许一个任务的状态更新到其他 SQL 标签页。

## 11. 前端状态管理

### 11.1 设计目标

建议使用 Pinia 管理全局状态。

避免所有状态都集中在一个 Store 中。

### 11.2 Store 划分

建议：

```
stores/
├── app.ts
├── connection.ts
├── explorer.ts
├── workspace.ts
├── query.ts
├── settings.ts
└── history.ts
```

职责：

| Store      | 职责                 |
| ---------- | -------------------- |
| app        | 应用全局状态         |
| connection | 数据源连接信息和状态 |
| explorer   | 数据库资源树         |
| workspace  | 标签和工作区         |
| query      | SQL 执行任务和结果   |
| settings   | 应用设置和主题       |
| history    | 查询历史             |

### 11.3 状态管理原则

- 全局共享状态放 Store。
- 组件内部临时状态放组件自身。
- 不重复保存可以从其他状态推导的数据。
- 后端真实状态优先于前端推测状态。
- 页面切换不能意外丢失正在执行任务的状态。
- 不能在多个 Store 中重复维护同一份连接状态。

## 12. 错误处理架构

### 12.1 统一错误类型

建议后端建立统一错误结构。

示例：

```
pub enum AppError {
    Validation(String),
    Connection(String),
    Database(String),
    Query(String),
    Storage(String),
    Credential(String),
    Task(String),
    Internal(String),
}
```

实际项目中还需要根据错误传播和序列化要求完善实现。

### 12.2 错误处理原则

- 底层错误应当保留必要上下文。
- 向前端返回可理解的信息。
- 不向 UI 暴露敏感连接信息。
- 不返回密码和完整连接字符串。
- 详细错误可以记录在本地日志。
- 不能静默吞掉异常。

### 12.3 前端错误展示

根据错误类型决定展示方式：

- 普通操作失败：Toast。
- 连接失败：连接弹窗展示。
- SQL 错误：查询结果消息区域展示。
- 严重内部异常：详细错误弹窗或日志入口。

## 13. 日志架构

### 13.1 日志目标

记录 DataDock 自身的运行日志。

包括：

- 应用启动。
- 应用退出。
- 数据库连接。
- SQL 执行。
- 本地存储异常。
- 后台任务。
- 系统凭据异常。
- 未处理异常。

### 13.2 日志等级

建议：

| 等级  | 用途         |
| ----- | ------------ |
| ERROR | 严重错误     |
| WARN  | 警告         |
| INFO  | 关键业务事件 |
| DEBUG | 调试信息     |
| TRACE | 详细执行信息 |

### 13.3 日志安全

禁止记录：

- 数据库密码。
- 完整敏感连接字符串。
- 系统凭据内容。
- 用户不希望进入日志的敏感 SQL 参数。

SQL 日志需要考虑隐私和安全。

建议提供 SQL 历史与运行日志的不同保存策略。

## 14. 数据导出架构

### 14.1 导出目标

V1.0 优先支持：

- CSV。
- JSON。

### 14.2 导出流程

```
用户点击导出
      |
      ▼
选择格式
      |
      ▼
选择保存路径
      |
      ▼
后端读取数据
      |
      ▼
按格式生成文件
      |
      ▼
写入目标文件
      |
      ▼
返回导出结果
```

### 14.3 导出要求

- 大数据量导出尽量采用流式处理。
- 不应一次性将所有数据加载到内存。
- 导出失败需要保留错误信息。
- 导出过程需要支持进度反馈。
- 用户取消导出时应当清理未完成的临时文件。
- CSV 需要正确处理引号、逗号和换行符。
- JSON 需要正确处理 NULL、数字、字符串等类型。

## 15. 安全架构

### 15.1 Tauri 安全

需要遵循 Tauri 安全开发原则。

包括：

- 使用合理的 Capability 配置。
- 仅开放必要的 IPC 能力。
- 不随意启用不必要的插件权限。
- 避免不可信内容进入 WebView。
- 避免动态执行不可信代码。
- 正确处理文件访问权限。

### 15.2 数据库操作安全

- 数据库密码使用系统凭据管理。
- 筛选条件使用参数化查询。
- 数据修改需要明确定位条件。
- 动态表名和字段名需要严格校验并正确转义。
- 对删除和批量修改操作提供确认。
- 不将敏感信息写入日志。

### 15.3 前端安全

- 不保存明文密码。
- 不将数据库密码放入 Pinia 持久化。
- 不通过浏览器 LocalStorage 保存敏感凭据。
- 不信任前端传入的 SQL 参数和资源标识。
- 后端必须再次校验权限和操作目标。

## 18. 性能设计

### 18.1 UI 性能

- 避免大型数据表一次性渲染全部记录。
- 大型结果集考虑虚拟滚动。
- Monaco Editor 按需初始化。
- 复杂页面按需加载。
- 避免不必要的全局状态更新。

### 18.2 数据库性能

- 合理使用连接池。
- 避免频繁创建和销毁连接。
- 查询结果采用分页或分批获取。
- 大数据量导出采用流式处理。
- 避免不必要的全表统计。
- 合理处理超时和异常。

### 18.3 任务性能

- SQL 执行放入异步任务。
- 不允许长时间数据库操作阻塞 UI。
- 对后台任务进行资源管理。
- 防止用户重复触发相同操作。
- 对并发任务设置合理限制。

## 21. AI 开发约束

AI 在实现 DataDock 时必须遵守：

1. 采用 Tauri 桌面应用架构。
2. 前端和 Rust 后端职责分离。
3. 前端不得直接连接远程数据库。
4. 所有远程数据库操作统一由后端执行。
5. Command 层不能堆积业务逻辑。
6. 业务逻辑放在 Service 层。
7. 本地 SQLite 操作统一通过 Repository。
8. 数据源操作通过 Adapter。
9. V1.0 只实现 MySQL，不提前实现 Redis 和 PostgreSQL。
10. 每个数据库连接必须独立管理。
11. SQL 执行必须支持异步任务管理。
12. SQL 任务必须具有独立 task_id。
13. 不能将取消 Rust 异步任务等同于数据库服务器已经停止执行。
14. 数据库密码不能明文存储在 SQLite 或前端状态中。
15. 不允许为了适配不同数据库而设计过度通用的接口。
16. 所有接口必须有明确的请求和响应类型。
17. 错误处理必须统一。
18. 重要操作必须有日志。
19. 所有依赖版本必须保持兼容。
20. 不得擅自增加云端服务或远程同步依赖。

## 23. 最终架构原则

DataDock 的架构需要遵循以下方向：

**前端负责交互，Rust 负责业务和数据访问，Adapter 负责数据源差异，SQLite 负责本地持久化，系统凭据服务负责敏感密码。**

V1.0 重点不是提前实现所有数据库类型，而是建立一套清晰、稳定、可扩展的 MySQL 数据库客户端架构。

在满足当前功能的前提下，为 Redis 和 PostgreSQL 留出合理的扩展位置。

不要过度抽象，不要过度设计，也不要为了未来可能出现的需求增加当前版本的复杂度。
