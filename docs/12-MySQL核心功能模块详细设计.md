
职责划分：

| 层级              | 主要职责                                   |
| ----------------- | ------------------------------------------ |
| Vue 前端          | 编辑器、表格、交互、状态展示               |
| Tauri Commands    | 接收前端请求、参数校验、返回结果           |
| Service           | 业务流程、任务协调、历史记录管理           |
| MySQL Adapter     | 数据库连接、SQL 执行、元数据查询、数据操作 |
| SQLite Repository | 本地配置、历史记录、SQL 收藏、工作区状态   |

必须遵守：

- 前端不能直接连接 MySQL。
- 前端不能直接操作 Rust 内部连接池。
- Tauri Command 不应该承担复杂业务逻辑。
- Service 不应该直接操作前端组件。
- MySQL 操作统一通过 MySQL Adapter。
- 本地 SQLite 操作统一通过 Repository。

# 3. SQL 编辑器模块

## 3.1 模块定位

SQL 编辑器是 DataDock 的核心操作入口。

用户通过 SQL 编辑器编写 SQL，选择目标数据源和数据库，然后执行查询或数据库操作。

V1 建议使用 Monaco Editor。

Monaco 只是编辑器组件，不负责数据库连接和 SQL 执行。

SQL 编辑器需要与 SQL 执行引擎、查询结果模块、查询历史模块协作。

## 3.2 编辑器基本功能

V1 需要实现：

| 功能         | 优先级 | 说明                       |
| ------------ | ------ | -------------------------- |
| SQL 语法高亮 | P0     | MySQL 语法高亮             |
| 行号显示     | P0     | 显示代码行号               |
| 当前行高亮   | P0     | 标识光标所在行             |
| 括号匹配     | P0     | 匹配括号                   |
| 自动缩进     | P0     | 基础代码缩进               |
| 多标签编辑   | P0     | 支持多个 SQL 编辑标签      |
| SQL 执行     | P0     | 执行当前语句或选中内容     |
| 全部执行     | P0     | 执行当前编辑器中的全部 SQL |
| 查找替换     | P1     | 编辑器内查找和替换         |
| SQL 格式化   | P1     | 格式化 SQL                 |
| 代码折叠     | P1     | 折叠 SQL 代码块            |
| 自动补全     | P1     | 关键字、表名、字段名       |
| SQL 提示     | P1     | 数据库对象提示             |

P0 是 V1 核心功能，P1 可以在核心功能稳定后完善。

## 3.3 编辑器技术结构

建议前端组件：

```
SqlEditor/
├── SqlEditor.vue
├── SqlEditorToolbar.vue
├── SqlEditorTabs.vue
├── SqlEditorStatusBar.vue
├── SqlCompletionProvider.ts
├── SqlLanguageProvider.ts
└── useSqlEditor.ts
```

职责：

| 组件                   | 职责                     |
| ---------------------- | ------------------------ |
| SqlEditor.vue          | Monaco 编辑器主体        |
| SqlEditorToolbar.vue   | 执行、停止、格式化等操作 |
| SqlEditorTabs.vue      | SQL 编辑标签             |
| SqlEditorStatusBar.vue | 光标位置、编辑状态等     |
| SqlCompletionProvider  | 自动补全                 |
| SqlLanguageProvider    | SQL 语言配置             |
| useSqlEditor           | 编辑器状态与操作封装     |

实际目录可以根据项目现有结构调整，不要求完全按照示例拆分。

## 3.4 编辑器工作区状态

建议每个编辑器标签维护独立状态：

```
interface SqlEditorTab {
    id: string;

    title: string;

    dataSourceId: string;

    database?: string;

    sql: string;

    dirty: boolean;

    activeTaskId?: string;

    createdAt: number;

    updatedAt: number;
}
```

字段说明：

- `id`：标签唯一标识。
- `title`：标签显示名称。
- `dataSourceId`：当前关联的数据源。
- `database`：当前默认数据库。
- `sql`：编辑器内容。
- `dirty`：是否存在未保存修改。
- `activeTaskId`：当前关联的执行任务。

多个编辑器标签必须相互独立。

切换标签时，需要恢复对应 SQL 内容、数据源和数据库上下文。

## 3.5 数据源与数据库上下文

每个 SQL 编辑器标签都应该明确当前使用的数据源。

例如：

```
SQL Tab 1
  数据源：开发数据库
  数据库：dev

SQL Tab 2
  数据源：测试数据库
  数据库：test

SQL Tab 3
  数据源：生产数据库
  数据库：production
```

执行 SQL 时，必须使用当前标签关联的数据源。

不能使用全局当前数据源代替每个标签的独立配置。

切换数据库时，应更新当前标签的数据库上下文。

如果用户更换数据源，需要明确提示数据库上下文已经改变，避免在错误的数据源中执行 SQL。

## 3.6 SQL 文件

V1 可以支持基本 SQL 文件操作：

- 新建 SQL 文件。
- 打开 SQL 文件。
- 保存 SQL 文件。
- 另存为。
- 未保存内容提示。
- 文件编码处理。

SQL 文件属于用户本地文件，不应默认保存到 DataDock SQLite 中。

工作区状态可以保存最近打开的文件路径和标签信息，但不应将本地文件内容重复保存为另一份长期副本，除非产品明确需要自动恢复能力。

## 3.7 SQL 自动补全

建议分为两类：

**静态补全**

- SELECT。
- INSERT。
- UPDATE。
- DELETE。
- CREATE。
- ALTER。
- DROP。
- JOIN。
- WHERE。
- GROUP BY。
- ORDER BY。

**动态补全**

- 当前数据库名称。
- 当前数据库中的表。
- 当前表中的字段。
- 视图名称。
- 索引名称。

动态补全的数据来源是 MySQL Adapter 提供的元数据查询能力。

建议在前端维护短期缓存：

```
dataSourceId + database
        |
        v
获取数据库元数据
        |
        v
缓存表名、字段名
        |
        v
Monaco Completion Provider
```

缓存需要考虑失效问题。

用户刷新数据库资源树或切换数据库后，应更新相关补全缓存。

自动补全不能阻塞编辑器输入。

## 3.8 快捷键

| ------------------------ | ---------------------------------- |

如果 Monaco 本身已经提供某项快捷键，优先使用原生能力，避免重复注册。

# 4. SQL 语句识别与执行请求

## 4.1 执行模式

SQL 编辑器需要支持三种执行模式：

```
CURRENT
SELECTION
ALL
```

说明：

| 模式      | 说明                       |
| --------- | -------------------------- |
| CURRENT   | 执行光标所在 SQL 语句      |
| SELECTION | 执行用户选中的 SQL         |
| ALL       | 执行当前编辑器中的全部 SQL |

## 4.2 当前语句识别

用户没有选中 SQL 时，按当前光标位置识别当前语句。

例如：

```
SELECT * FROM users;

SELECT * FROM orders;

UPDATE users
SET status = 1
WHERE id = 1;
```

如果光标位于第二条 SELECT 语句中，则只执行第二条。

不能直接使用最近的分号和下一个分号简单截取 SQL，因为 SQL 可能包含：

- 字符串中的分号。
- 单行注释。
- 多行注释。
- 存储过程。
- 复杂语法结构。

建议使用 MySQL 语法分析能力或经过充分测试的 SQL 分句器。

如果暂时没有合适的解析能力，可以先实现覆盖常见 SQL 的分句逻辑，并明确标注不支持的语法场景。

不能将简单的字符串分割描述成完整的 MySQL 语法解析器。

## 4.3 SQL 执行请求

建议统一请求结构：

```
interface ExecuteSqlRequest {
    taskId: string;

    dataSourceId: string;

    database?: string;

    sql: string;

    parameters?: unknown[];

    executionMode: "current" | "selection" | "all";
}
```

注意：

- `taskId` 用于关联执行任务。
- `dataSourceId` 决定连接目标。
- `database` 表示当前默认数据库。
- `sql` 是本次实际执行的 SQL 内容。
- `parameters` 用于参数化执行。

执行前端传入的 SQL 时，不应该擅自添加、删除或修改用户 SQL。

如果执行模式为 ALL，需要明确多语句处理策略。

## 4.4 执行流程

```
用户点击执行
      |
      v
获取当前编辑器内容
      |
      v
判断执行模式
      |
      +---- CURRENT
      |       |
      |       v
      |   识别当前语句
      |
      +---- SELECTION
      |       |
      |       v
      |   获取选中内容
      |
      +---- ALL
              |
              v
          获取全部内容
      |
      v
校验数据源和 SQL
      |
      v
创建执行任务
      |
      v
提交 Rust 后端
      |
      v
MySQL Adapter 执行
      |
      v
读取执行结果
      |
      v
更新查询历史
      |
      v
通知前端
      |
      v
展示结果
```

## 4.5 执行前校验

执行前至少检查：

- 数据源是否存在。
- 数据源是否处于可执行状态。
- SQL 是否为空。
- 当前数据库上下文是否有效。
- 当前任务是否重复提交。
- 执行参数是否符合请求结构。

不能在前端校验通过后，就认为后端不需要再次校验。

后端必须进行必要的参数校验。

## 4.6 执行状态

建议统一状态：

```
type QueryTaskStatus =
    | "pending"
    | "running"
    | "cancelling"
    | "success"
    | "failed"
    | "cancelled";
```

任务状态变化：

```
PENDING
   |
   v
RUNNING
   |
   +----> SUCCESS
   |
   +----> FAILED
   |
   +----> CANCELLING
              |
              v
          CANCELLED
```

如果取消请求未能确认服务端执行已经终止，不能直接将任务标记为已取消。

## 4.7 SQL 执行时间

需要记录：

- 任务创建时间。
- 开始执行时间。
- 完成时间。
- 总耗时。

耗时建议由 Rust 后端计算。

前端显示的耗时可以实时刷新，但最终统计数据以 Rust 后端返回为准。

# 5. SQL 执行引擎

## 5.1 模块职责

SQL 执行引擎负责：

- 接收 SQL 执行请求。
- 创建执行任务。
- 选择对应数据源。
- 调用 MySQL Adapter。
- 收集执行结果。
- 管理查询任务状态。
- 处理任务取消。
- 将结果传递给前端。
- 通知查询历史模块。

SQL 执行引擎不负责 Monaco 编辑器界面，也不负责结果表格的渲染。

## 5.2 任务管理

建议由 Rust 后端维护 QueryTaskManager。

逻辑结构：

```
QueryTaskManager
    |
    +---- Task A
    |        |
    |        +---- DataSource A
    |        +---- SQL
    |        +---- Status
    |        +---- Result
    |
    +---- Task B
    |        |
    |        +---- DataSource B
    |        +---- SQL
    |        +---- Status
    |        +---- Result
    |
    +---- Task C
             |
             +---- DataSource A
             +---- SQL
             +---- Status
             +---- Result
```

任务必须有唯一标识。

不能只通过编辑器标签 ID 判断任务，因为同一个编辑器可以多次执行 SQL。

## 5.3 任务信息

建议：

```
pub struct QueryTask {
    pub task_id: String,

    pub data_source_id: String,

    pub database: Option<String>,

    pub sql: String,

    pub status: QueryTaskStatus,

    pub created_at: i64,

    pub started_at: Option<i64>,

    pub finished_at: Option<i64>,
}
```

任务运行过程中可能需要额外维护：

- 执行连接信息。
- 当前语句序号。
- 结果集读取状态。
- 取消请求状态。
- 错误信息。
- 结果缓存或读取游标。

这些运行时状态不一定全部需要持久化到 SQLite。

## 5.4 并发执行

不同数据源的查询任务可以并发执行。

同一数据源的任务也可以并发执行，但必须受到连接池和任务数量限制。

建议：

- 任务数量有上限。
- 单数据源并发数可配置。
- 超出限制时返回明确错误或进入等待队列。
- 不能无限创建异步任务。
- 单个任务失败不影响其他任务。

## 5.5 查询取消

前端停止按钮调用取消接口。

```
interface CancelQueryRequest {
    taskId: string;
}
```

流程：

```
用户点击停止
      |
      v
前端发送取消请求
      |
      v
Rust 查询任务管理器
      |
      v
查找 taskId
      |
      v
检查任务状态
      |
      v
调用 Adapter 取消机制
      |
      v
更新任务状态
      |
      v
通知前端
```

取消机制的实际效果依赖 MySQL 驱动能力和具体实现。

必须区分取消等待、停止结果读取和真正终止服务端 SQL。

如果驱动不支持可靠取消，应在 V1 中明确限制，不能伪装成已经完成服务端取消。

## 5.6 任务清理

任务完成后，需要根据结果保存策略释放运行时资源。

建议：

- 完成任务保留必要的结果摘要。
- 大型结果集采用分批读取或临时缓存。
- 已关闭编辑器不代表任务自动结束。
- 应用退出时停止接收新任务，并按合理顺序清理运行任务和连接。
- 过期任务应定期清理运行时状态。

任务历史记录由查询历史模块持久化。

# 6. 查询结果管理

## 6.1 模块定位

查询结果模块负责接收 SQL 执行引擎返回的数据，并展示查询结果。

主要包括：

- 结果集表格。
- 结果列信息。
- 多结果集切换。
- 执行状态。
- 影响行数。
- 执行耗时。
- 错误信息。
- 数据复制。
- 结果导出。

## 6.2 结果结构

建议：

```
interface QueryResultSet {
    resultSetId: string;

    statementIndex: number;

    columns: ColumnDefinition[];

    rows: CellValue[][];

    fetchedRows: number;

    hasMore: boolean;

    affectedRows?: string;

    durationMs: number;
}
```

一个 SQL 执行任务可以包含多个 StatementResult。

每条语句也可能包含多个结果集，具体取决于驱动和数据库返回能力。

因此，结果结构应允许扩展为：

```
interface StatementResult {
    statementIndex: number;

    statementType: string;

    resultSets: QueryResultSet[];

    affectedRows?: string;

    durationMs: number;

    error?: QueryError;
}
```

对于 INSERT、UPDATE、DELETE 等没有普通结果集的语句，`resultSets` 可以为空。

## 6.3 结果展示布局

结果区域建议沿用已有 UI 设计规范。

```
┌──────────────────────────────────────────┐
│ SQL 编辑器                               │
│                                          │
│ SELECT * FROM users;                     │
│                                          │
├──────────────────────────────────────────┤
│ 结果 | 消息 | 执行日志                   │
├──────────────────────────────────────────┤
│ id  │ username │ status │ created_at     │
│ 1   │ admin    │ 1      │ ...            │
│ 2   │ user     │ 1      │ ...            │
│ 3   │ test     │ 0      │ ...            │
├──────────────────────────────────────────┤
│ 已加载 100 行     耗时 25ms              │
└──────────────────────────────────────────┘
```

具体布局和尺寸遵循 `02-UI与交互设计规范.md`。

## 6.4 多结果集展示

例如：

```
SELECT * FROM users;

SELECT * FROM orders;
```

需要允许用户在多个结果集之间切换。

建议：

```
结果 1
结果 2
结果 3
```

每个结果集独立维护：

- 列定义。
- 当前页数据。
- 加载状态。
- 是否还有更多数据。
- 错误状态。

不能将不同 SQL 的结果合并成一张表。

## 6.5 查询结果分页

结果集可能非常大。

建议使用批量读取机制：

```
第一次请求
    |
    v
读取第一批数据
    |
    v
展示结果
    |
    v
用户加载更多
    |
    v
继续读取后续数据
```

是否能够在首次执行后继续读取，取决于底层驱动是否支持保持结果读取状态。

如果不能安全地保持游标或连接状态，则需要设计明确的重新查询策略。

不能直接将 LIMIT/OFFSET 加到用户原始 SQL 中，假装支持通用结果分页。

需要区分：

1. 数据浏览器分页：由 DataDock 生成查询 SQL。
2. SQL 编辑器结果集分批读取：由执行引擎控制读取过程。

两者不是同一种实现。

## 6.6 结果列宽与展示

建议：

- 列宽支持自动计算。
- 支持手动调整列宽。
- 长文本默认截断预览。
- 鼠标悬停或单元格详情查看完整内容。
- NULL 使用明显但不影响阅读的样式。
- 二进制字段显示摘要。
- BIGINT、DECIMAL 使用精确字符串展示。
- 日期时间保留正确格式。

单元格截断必须有提示。

不能让用户误以为显示内容就是完整数据。

## 6.7 结果复制

V1 建议支持：

- 复制当前单元格。
- 复制当前行。
- 复制选中区域。
- 复制为 TSV。
- 复制为 CSV 格式文本。

复制操作应尽量保留原始数据内容。

对于包含制表符、换行和引号的数据，需要正确转义。

## 6.8 结果导出

V1 建议支持：

- CSV。
- JSON。

后续可以增加：

- Excel。
- SQL INSERT。
- XML。

导出流程：

```
用户点击导出
      |
      v
选择导出格式
      |
      v
确认导出范围
      |
      v
获取完整数据
      |
      v
Rust 或前端生成文件
      |
      v
用户选择保存位置
      |
      v
完成导出
```

导出实现位置可以根据数据规模决定。

小型数据集可以由前端处理，大型数据集建议由 Rust 后端流式生成文件，避免前端内存占用过大。

导出时需要明确：

- 导出当前已加载数据。
- 导出完整查询结果。
- 导出当前筛选结果。

不能将只导出了当前已加载数据的操作标记成完整结果导出。

## 6.9 执行消息

除结果集外，还需要展示执行消息。

例如：

```
查询执行成功
影响行数：1
执行耗时：12ms
```

失败时：

```
执行失败
错误代码：1064
错误信息：SQL 语法错误
```

执行消息和结果集应分开管理。

# 7. 查询历史与 SQL 收藏

## 7.1 模块定位

查询历史负责记录用户执行过的 SQL。

SQL 收藏用于保存用户经常使用的 SQL 语句。

两者属于本地数据，不依赖云端。

相关数据库表已经在 `04-数据库设计.md` 中定义。

本模块主要定义业务行为。

## 7.2 查询历史记录时机

建议在 SQL 执行任务创建后记录一条历史。

初始状态：

```
running
```

任务完成后更新：

```
success
failed
cancelled
```

不要只在 SQL 执行成功后记录历史。

否则用户无法查看失败的 SQL。

## 7.3 历史记录内容

建议保存：

- SQL 内容。
- 数据源 ID。
- 数据库名称。
- 执行状态。
- 执行耗时。
- 影响行数。
- 返回行数。
- 错误信息。
- 创建时间。
- 完成时间。

查询历史默认按时间倒序排列。

## 7.4 历史记录查询

建议支持：

- 按数据源筛选。
- 按数据库筛选。
- 按执行状态筛选。
- 按 SQL 内容搜索。
- 按时间范围筛选。

历史列表应支持分页或分批加载。

不能一次性加载全部历史记录。

## 7.5 重新执行

用户可以选择一条历史记录重新执行。

流程：

```
选择历史记录
      |
      v
读取 SQL 内容
      |
      v
检查原数据源
      |
      v
检查数据源连接状态
      |
      v
打开或切换 SQL 编辑器
      |
      v
恢复 SQL 内容
      |
      v
用户确认执行
```

重新执行时不能默认立即执行高危 SQL。

应先恢复到编辑器，由用户主动确认执行。

如果原数据源已被删除，应提示用户重新选择数据源。

## 7.6 SQL 收藏

收藏记录建议支持：

- 收藏名称。
- SQL 内容。
- 所属数据源（可选）。
- 所属数据库（可选）。
- 备注。
- 创建时间。
- 更新时间。

收藏不应该强制绑定某个数据源。

例如：

```
SELECT *
FROM users
WHERE status = 1;
```

这条 SQL 可以在多个环境中使用。

用户打开收藏时，可以选择目标数据源。

## 7.7 查询历史清理

建议支持：

- 删除单条历史。
- 批量删除。
- 清空历史。
- 按保留时间清理。

清理历史不应该影响 SQL 收藏。

清理历史也不应该影响远程数据库。

## 7.8 隐私保护

查询历史可能包含敏感 SQL 或业务数据。

需要注意：

- 历史记录只保存在本地 SQLite。
- 不上传云端。
- 不将 SQL 内容默认写入普通日志。
- 删除历史时清理对应本地记录。
- 对敏感信息的记录策略应提供后续扩展能力。

# 8. 数据浏览器模块

## 8.1 模块定位

数据浏览器用于通过图形化界面查看和操作数据库表中的数据。

它与 SQL 编辑器是两个不同的入口：

| 模块       | 主要用途               |
| ---------- | ---------------------- |
| SQL 编辑器 | 执行用户编写的 SQL     |
| 数据浏览器 | 图形化查看和编辑表数据 |

数据浏览器生成的 SQL 由后端负责构造。

用户不需要手动编写 SQL 就可以完成基础数据管理。

## 8.2 页面结构

建议：

```
数据浏览器
│
├── 顶部工具栏
│   ├── 刷新
│   ├── 新增
│   ├── 删除
│   ├── 保存
│   ├── 取消修改
│   └── 导出
│
├── 筛选区域
│
├── 数据表格
│
└── 分页区域
```

具体视觉样式遵循已有 UI 设计规范。

## 8.3 打开数据表

用户在资源树中双击表节点。

流程：

```
双击数据表
      |
      v
读取数据源 ID
      |
      v
读取数据库名称
      |
      v
读取表名称
      |
      v
获取表结构
      |
      v
生成数据浏览器标签
      |
      v
加载第一页数据
```

数据浏览器标签建议包含：

```
interface TableBrowserTab {
    id: string;

    dataSourceId: string;

    database: string;

    table: string;

    page: number;

    pageSize: number;

    sortConditions: SortCondition[];

    filters: FilterCondition[];

    dirty: boolean;
}
```

每个表数据浏览器标签独立维护状态。

## 8.4 数据查询

查询请求：

```
interface FetchTableDataRequest {
    dataSourceId: string;

    database: string;

    table: string;

    page: number;

    pageSize: number;

    sort?: SortCondition[];

    filters?: FilterCondition[];
}
```

Rust 后端负责：

1. 校验数据源。
2. 校验数据库。
3. 校验表名。
4. 获取表结构。
5. 校验排序字段。
6. 校验筛选字段。
7. 校验操作符。
8. 构造 SQL。
9. 使用参数化查询。
10. 返回数据。

前端不能自行拼接完整 SQL 后传给后端执行。

## 8.5 分页

V1 建议默认每页 100 条。

可选：

```
50
100
200
500
```

分页请求需要校验：

- 页码不能小于 1。
- 每页数量必须在允许范围内。
- offset 计算不能溢出。
- 查询结果必须按照指定排序规则返回。

如果用户没有设置排序，应尽可能采用主键或唯一索引作为稳定排序依据。

如果表没有可靠的排序字段，不应承诺分页结果在数据持续变化时始终稳定。

## 8.6 排序

支持：

- 单列升序。
- 单列降序。
- 多列排序（可以后续完善）。

排序字段必须来自当前表结构。

排序方向只能是 ASC 或 DESC。

排序字段不能直接使用未经验证的 SQL 字符串。

## 8.7 筛选

V1 建议支持：

- 等于。
- 不等于。
- 大于。
- 大于等于。
- 小于。
- 小于等于。
- LIKE。
- IS NULL。
- IS NOT NULL。

后续可以增加：

- IN。
- BETWEEN。
- NOT LIKE。
- 多条件 AND/OR。
- 字段类型相关筛选控件。

筛选值必须参数化。

复杂筛选条件应使用结构化表达式传递，不允许将任意 SQL 片段作为筛选条件。

## 8.8 数据类型展示

数据浏览器使用 MySQL Adapter 返回的类型信息。

需要正确处理：

- 整数。
- 浮点数。
- DECIMAL。
- BIGINT。
- 字符串。
- 长文本。
- 日期时间。
- JSON。
- ENUM。
- SET。
- 二进制。
- NULL。

不能仅根据前端收到的 JSON 值判断字段类型。

应结合列结构信息决定展示方式。

## 8.9 数据刷新

用户点击刷新时：

1. 清除当前页临时缓存。
2. 重新执行查询。
3. 保持合理的分页位置。
4. 更新数据列表。
5. 清理已经失效的编辑状态。

如果当前存在未保存修改，应先提示用户保存或放弃修改。

不能静默丢弃用户编辑的数据。

# 9. 表数据编辑

## 9.1 编辑模型

建议采用本地暂存、显式保存的编辑模式。

用户修改数据后，前端先保存临时修改状态。

用户点击保存后，再提交给 MySQL。

流程：

```
加载数据
   |
   v
用户修改单元格
   |
   v
记录本地修改
   |
   v
显示未保存状态
   |
   v
用户点击保存
   |
   v
提交 Rust 后端
   |
   v
执行数据库更新
   |
   v
检查影响行数
   |
   v
更新本地状态
```

不建议默认每次修改单元格就立即执行 UPDATE。

这样可以避免用户输入过程中产生大量数据库请求。

## 9.2 编辑状态

建议：

```
interface RowEditState {
    rowKey: string;

    originalValues: Record<string, unknown>;

    modifiedValues: Record<string, unknown>;

    status: "unchanged" | "modified" | "inserted" | "deleted";
}
```

说明：

- `unchanged`：没有修改。
- `modified`：已有记录发生修改。
- `inserted`：新增记录。
- `deleted`：待删除记录。

## 9.3 新增记录

用户点击新增后，创建一条本地临时记录。

字段初始化规则：

- 自增主键可以为空。
- 有默认值的字段可以使用默认值。
- 允许 NULL 的字段可以为空。
- 必填字段需要用户填写。
- JSON 字段需要校验格式。

点击保存后，Rust 后端根据表结构生成 INSERT。

如果插入成功，返回主键或其他必要信息，然后刷新数据列表。

## 9.4 修改记录

修改请求建议：

```
interface UpdateRowRequest {
    dataSourceId: string;

    database: string;

    table: string;

    primaryKey: Record<string, unknown>;

    changes: Record<string, unknown>;

    originalValues?: Record<string, unknown>;
}
```

其中 `primaryKey` 只是示意。

实际定位条件可能来自唯一索引或复合唯一键。

需要根据 MySQL Adapter 的表结构元数据确定可靠的行定位条件。

## 9.5 删除记录

删除操作需要用户确认。

建议支持：

- 删除当前选中行。
- 删除多条选中记录。

对于批量删除，后端需要明确预计影响的记录数量，并在执行后返回实际影响行数。

如果无法可靠定位记录，则不允许直接删除。

## 9.6 无主键表

无主键表是数据编辑中的特殊情况。

建议 V1 采用保守策略：

- 可以查看数据。
- 可以分页和筛选。
- 默认禁用直接修改。
- 默认禁用直接删除。
- 不允许根据不唯一字段静默修改多条记录。

如果后续需要支持无主键表编辑，应设计单独的行定位策略，并经过实际验证。

## 9.7 复合主键

例如：

```
CREATE TABLE user_roles (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    status TINYINT NOT NULL,
    PRIMARY KEY (user_id, role_id)
);
```

定位记录时必须使用完整主键：

```
UPDATE user_roles
SET status = ?
WHERE user_id = ?
  AND role_id = ?;
```

不能只使用其中一个字段。

## 9.8 修改冲突

用户打开数据后，其他客户端可能修改同一条记录。

建议保存时进行原始值比较。

如果数据库中的原始值已经发生变化，应提示用户：

```
当前记录可能已被其他用户修改。

请刷新数据后重新编辑。
```

对于复杂字段、NULL 和二进制字段，需要使用类型正确的比较逻辑。

## 9.9 保存结果

修改操作必须返回：

- 是否成功。
- 实际影响行数。
- 新生成的主键（如果适用）。
- 错误信息。
- 是否存在数据冲突。

前端不能只根据请求是否返回成功，就认定所有目标记录都已经正确修改。

# 10. 模块之间的协作

## 10.1 SQL 编辑器与执行引擎

SQL 编辑器只负责准备 SQL 和发起请求。

SQL 执行引擎负责执行任务。

两者通过统一请求结构通信。

编辑器不应该直接依赖 MySQL 驱动实现。

## 10.2 执行引擎与结果管理

SQL 执行引擎负责产生结果。

结果管理负责接收、缓存和展示结果。

建议通过任务 ID 关联：

```
taskId
  |
  +---- SQL 编辑器
  |
  +---- QueryTaskManager
  |
  +---- QueryResultManager
  |
  +---- QueryHistoryService
```

这样可以支持：

- 多标签执行。
- 多任务并行。
- 多结果集切换。
- 历史记录更新。
- 任务状态恢复。

## 10.3 执行引擎与查询历史

任务创建时，写入历史初始记录。

任务结束时，更新历史状态。

建议采用以下时序：

```
创建任务
   |
   v
写入 running 历史
   |
   v
执行 SQL
   |
   v
收集结果
   |
   v
任务结束
   |
   v
更新历史状态
```

如果本地历史写入失败，不应该因此篡改已经成功的远程 SQL 执行结果。

应记录本地持久化错误，并向用户提供合理提示。

## 10.4 数据浏览器与 MySQL Adapter

数据浏览器不应该自己构造并执行 SQL。

它通过 TableDataService 提交结构化请求。

TableDataService 负责参数校验、权限边界和业务处理。

MySQL Adapter 负责具体 SQL 生成与数据库操作。

## 10.5 统一错误处理

所有模块应使用统一错误结构。

建议区分：

```
ValidationError
ConnectionError
AuthenticationError
SqlExecutionError
QueryCancelled
Timeout
DataConflict
SerializationError
UnsupportedOperation
InternalError
```

前端根据错误类型展示合适提示。

不应该在每个 Vue 组件中重复解析 Rust 底层错误字符串。

# 12. 本地状态与持久化

## 12.1 持久化原则

需要持久化：

- 查询历史。
- SQL 收藏。
- 编辑器工作区状态。
- 最近打开的 SQL 文件信息。
- 必要的应用设置。

不需要默认持久化：

- 当前查询结果全部内容。
- 大型结果集完整数据。
- 正在运行的数据库连接对象。
- Rust 运行时任务对象。
- 数据库密码明文。

## 12.2 工作区恢复

应用启动后，可以恢复：

- 上次打开的 SQL 标签。
- 标签名称。
- 数据源关联。
- 数据库上下文。
- SQL 文件路径。
- 编辑器布局。

但恢复 SQL 标签不代表自动恢复数据库连接。

用户需要重新建立数据库连接，或由应用按照明确的连接恢复策略重新连接。

## 12.3 结果缓存

V1 可以采用内存缓存管理查询结果。

不建议默认将所有查询结果写入 SQLite。

如果未来需要持久化查询结果，应独立设计缓存生命周期、磁盘空间限制和敏感数据保护策略。

# 13. 安全与数据保护

## 13.1 SQL 注入防护

所有数据浏览器生成的 SQL 必须满足：

- 值参数化。
- 标识符安全引用。
- 排序字段白名单。
- 筛选操作符白名单。
- 不允许任意 SQL 片段注入。

SQL 编辑器允许用户执行任意 SQL，这是产品功能，不应该与数据浏览器的参数化查询混为一谈。

## 13.2 高危 SQL 提示

以下操作建议进行风险提醒：

- DROP DATABASE。
- DROP TABLE。
- TRUNCATE TABLE。
- 无 WHERE 的 DELETE。
- 无 WHERE 的 UPDATE。
- 修改大量记录的操作。

风险识别应尽量基于 SQL 语法分析。

不能仅靠简单正则表达式判断 SQL 是否安全。

对于无法正确解析的 SQL，可以采取保守提示策略。

但不能在没有产品决策的情况下，擅自禁止用户执行所有无法识别的合法 SQL。

## 13.3 数据修改保护

数据浏览器必须：

- 修改前保存原始值。
- 删除前确认。
- 无可靠唯一键时禁止危险修改。
- 检查影响行数。
- 识别可能的并发冲突。
- 对保存失败的数据保留合理的编辑状态。

## 13.4 数据源隔离

不同数据源之间：

- 连接实例隔离。
- 查询任务隔离。
- 结果集隔离。
- 数据浏览器上下文隔离。
- 查询历史能够准确关联数据源。

任何模块都不能通过一个全局连接对象随意切换数据库执行任务。

# 14. 性能设计

## 14.1 前端性能

- Monaco Editor 应避免重复初始化。
- 编辑器标签切换时尽量保留编辑状态。
- 结果表格采用虚拟滚动或其他适合大数据量的渲染方案。
- 大结果集采用分批加载。
- 不在 Vue 响应式状态中无必要地复制大型结果数据。
- 动态补全使用缓存。
- 频繁筛选输入适当防抖。

## 14.2 Rust 后端性能

- 数据库访问使用异步执行。
- 每个数据源使用独立连接管理。
- 限制并发任务数量。
- 使用流式读取或分批读取。
- 控制 IPC 数据量。
- 大型导出采用流式文件生成。
- 任务完成后及时释放资源。

## 14.3 IPC 性能

前后端之间不应该一次性传递大量数据。

建议：

```
Rust 读取数据
      |
      v
批量转换
      |
      v
批量序列化
      |
      v
Tauri IPC
      |
      v
Vue 更新结果
```

每批数据量应通过实际性能测试确定。

不要为了减少 IPC 次数而无限扩大单批数据量。

# 19. 设计总结

DataDock V1 的核心使用流程是：

```
创建 MySQL 数据源
       |
       v
连接数据库
       |
       v
浏览数据库资源
       |
       +-----------------------+
       |                       |
       v                       v
   SQL 编辑器              数据浏览器
       |                       |
       v                       v
   执行 SQL                查询表数据
       |                       |
       v                       v
   查询结果                数据编辑
       |                       |
       v                       v
   查询历史                保存修改
       |
       v
   SQL 收藏
```

整个系统应围绕以下原则实现：

- 编辑器负责 SQL 编写。
- 执行引擎负责 SQL 任务。
- MySQL Adapter 负责数据库访问。
- 查询结果负责数据展示。
- 查询历史负责本地记录。
- 数据浏览器负责图形化数据管理。
- SQLite 负责应用本地数据。
- 系统凭据服务负责数据库密码保护。

V1 的核心目标不是实现所有高级数据库管理功能，而是完成一个稳定、实用、具备良好交互体验的 MySQL 桌面管理工具。

在上述核心能力稳定后，再扩展 PostgreSQL、Redis 等数据源。
