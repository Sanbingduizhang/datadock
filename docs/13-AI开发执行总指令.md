# DataDock AI 开发执行总指令

> 文档路径：`docs/13-AI开发执行总指令.md`
> 文档用途：指导 AI 编码工具按照 DataDock 项目设计文档，逐阶段完成项目开发、测试、修复和交付。
> 适用对象：具备项目文件读取、代码编写、终端命令执行、测试和构建能力的 AI 编码工具。
> 执行原则：先理解项目，再检查现状；先搭建基础，再逐步实现；每个阶段必须验证，不允许一次性生成整个项目。

# 一、项目开发总要求

## 1.1 项目基本信息

项目名称：DataDock。

项目定位：面向开发者的轻量级桌面多数据源管理工具。

项目目标：开发一款跨平台桌面数据库管理工具，优先实现 MySQL 管理能力，后续扩展 Redis、PostgreSQL 等数据源。

产品版本规划：

| 版本 | 主要内容                         |
| ---- | -------------------------------- |
| V1   | MySQL 数据源管理及核心数据库操作 |
| V2   | Redis 数据源管理                 |
| V3   | PostgreSQL 数据源管理            |

核心技术方向：

- 桌面应用：Tauri。
- 前端：Vue 3。
- 前端语言：TypeScript。
- 前端构建：Vite。
- 状态管理：Pinia。
- SQL 编辑器：Monaco Editor，具体集成方式以技术验证结果为准。
- 后端：Rust。
- 异步运行时：Tokio，具体以最终依赖方案为准。
- 本地数据库：SQLite。
- 远程数据库：V1 优先支持 MySQL。
- 系统凭据：使用操作系统提供的安全凭据存储机制。

以上内容是项目的技术方向。具体依赖版本、数据库驱动及实现方式，应以项目设计文档和实际技术验证结果为准。

## 1.2 最重要的开发原则

AI 必须遵守以下原则：

1. 严格按照项目设计文档开发，不得自行改变已经确定的产品方向。
2. 不得擅自更换核心技术架构。
3. 不得为了减少代码量而省略核心功能。
4. 不得将本应由 Rust 后端负责的数据库连接、SQL 执行等逻辑放到 Vue 前端。
5. 不得让前端直接连接远程数据库。
6. 不得将数据库密码明文保存到 SQLite、Pinia、localStorage 或普通配置文件中。
7. 不得将多个数据源的连接状态、查询结果和任务状态混在一起。
8. 不得使用 Mock 数据冒充已经完成的真实功能。
9. 不得在未验证技术能力的情况下宣称某项功能已经实现。
10. 每完成一个开发阶段，都必须执行相应测试和构建验证。
11. 不得一次性生成所有模块代码。
12. 不得随意删除、覆盖或重写项目中已有的代码和配置。
13. 遇到设计文档冲突时，必须先分析并报告，不得自行选择一个方案直接大范围修改。
14. 所有未完成的功能、限制和已知问题必须如实记录。

**开发质量优先于代码生成速度。**

# 三、项目技术架构约束

## 3.1 整体架构

DataDock 使用桌面应用架构：

前端 Vue 负责界面展示和用户交互。

Rust 后端负责数据库连接、SQL 执行、本地存储、任务管理及系统能力调用。

Tauri IPC 负责前后端通信。

整体结构：

```
DataDock
│
├── Vue 3 前端
│   ├── 页面展示
│   ├── 组件交互
│   ├── 状态管理
│   ├── SQL 编辑器
│   ├── 数据表格
│   └── 调用 Tauri Commands
│
├── Tauri IPC
│   ├── Command 请求
│   └── Event 事件通知
│
├── Rust 后端
│   ├── Commands
│   ├── Services
│   ├── Repositories
│   ├── Adapters
│   ├── Task Manager
│   ├── SQLite
│   └── Credential Manager
│
└── 远程数据库
    ├── MySQL
    ├── Redis（V2）
    └── PostgreSQL（V3）
```

## 3.2 前后端职责

### Vue 前端

负责：

- 页面和组件。
- 数据源管理界面。
- 数据库资源树。
- SQL 编辑器。
- 查询结果展示。
- 表数据浏览。
- 表结构展示。
- 查询历史。
- SQL 收藏。
- 用户交互。
- 前端状态管理。

不负责：

- 直接建立 MySQL 网络连接。
- 直接执行远程数据库 SQL。
- 保存数据库密码。
- 管理数据库连接池。
- 执行需要高权限的系统凭据操作。

### Rust 后端

负责：

- 数据库连接管理。
- 数据源适配器。
- SQL 执行。
- 查询任务管理。
- 查询结果读取。
- 元数据查询。
- 表数据操作。
- SQLite 本地存储。
- 系统凭据管理。
- 数据导出。
- 错误处理。
- 日志记录。

## 3.3 数据源隔离

每个数据源必须拥有独立的连接实例或连接池。

不同数据源之间必须隔离：

- 连接状态。
- 数据库上下文。
- SQL 执行任务。
- 查询结果。
- 错误信息。
- 事务状态。
- 资源树状态。

不得使用一个全局连接承载所有数据源的操作。

## 3.4 数据源适配器

必须遵循适配器架构。

MySQL 的实现应放在独立的 MySQL Adapter 中。

后续 Redis、PostgreSQL 应使用独立适配器。

不能将 MySQL 的数据库、表、字段等数据模型强制应用到 Redis。

可以抽象通用的数据源连接、状态和能力接口，但具体数据源功能必须保留自身特点。

## 3.5 本地数据与远程数据

必须区分两类数据：

**本地数据：**

- 数据源连接配置。
- 查询历史。
- SQL 收藏。
- 应用设置。
- 工作区状态。

使用本地 SQLite 存储。

**远程数据：**

- 数据库。
- 表。
- 视图。
- 字段。
- 索引。
- 表数据。
- SQL 执行结果。

通过对应的数据源适配器访问。

不得将远程数据库的数据误认为本地 SQLite 数据。

## 3.6 密码安全

数据库密码不得明文存储。

推荐使用操作系统凭据管理机制：

- macOS：Keychain。
- Windows：Credential Manager。
- Linux：Secret Service 或经过验证的等效机制。

SQLite 只保存凭据引用，例如 `credential_key`。

前端不得持久化数据库密码。

连接测试、保存、读取和删除密码必须经过 Rust 后端安全处理。

如果当前操作系统的凭据能力无法使用，必须明确报告，不得静默退化为明文保存。

### SQL 执行模式

必须支持三种执行方式：

| 模式      | 行为                      |
| --------- | ------------------------- |
| CURRENT   | 执行当前光标所在 SQL 语句 |
| SELECTION | 执行用户选中的 SQL        |
| ALL       | 执行编辑器中的全部 SQL    |

必须正确处理 SQL 语句边界。

不能简单使用分号切割 SQL，因为字符串、注释、存储过程等场景可能存在复杂情况。

需要根据驱动能力和 SQL 解析方案确定实现方式。

### 查询任务管理

每个查询任务必须有独立 task_id。

任务状态至少包括：

- pending。
- running。
- success。
- failed。
- cancelled。

需要处理：

- 多任务并发。
- 任务状态更新。
- 查询结果归属。
- 任务异常。
- 任务清理。
- 用户取消。
- 连接关闭时的任务处理。

不得使用一个全局变量保存当前查询任务。

### 查询取消要求

必须区分：

1. 前端停止等待结果。
2. Rust 后端停止处理当前任务。
3. 数据库服务端真正停止执行 SQL。

只有底层驱动真正支持并成功执行服务端取消操作，才能向用户报告数据库查询已停止。

不得通过简单取消 Future 或关闭前端加载动画，就宣称数据库查询已经终止。

### 查询结果要求

- 支持多结果集。
- 支持列信息展示。
- 支持 NULL。
- 支持常见 MySQL 类型。
- 支持大整数精度保护。
- 支持 DECIMAL 精度保护。
- 支持复制结果。
- 支持 CSV 导出。
- 支持 JSON 导出。
- 支持大结果集分批读取。

普通查询的结果展示限制不能通过修改用户原始 SQL 的方式粗暴实现。

### 验收标准

- 可以编辑 SQL。
- 可以执行当前语句。
- 可以执行选中语句。
- 可以执行全部 SQL。
- 可以查看执行结果。
- 可以处理执行错误。
- 可以管理多个查询任务。
- 可以记录查询历史。
- 可以收藏 SQL。
- 查询结果不会错误地显示到其他数据源或标签页。
- SQL 执行期间 UI 不会卡死。

### 分页要求

- 50 条。
- 100 条。
- 200 条。
- 500 条。

对于简单分页，可以使用 LIMIT/OFFSET。

对于大偏移量导致的性能问题，后续可以评估 Keyset Pagination。

### 安全要求

- SQL 标识符。
- SQL 参数值。

标识符必须经过安全引用和白名单验证。

筛选值必须参数化。

不得直接将前端传来的字段名和值拼接成未经验证的 SQL。

### 验收标准

# 五、每个阶段的标准执行流程

所有开发阶段必须按照以下流程执行。

## 5.1 第一步：明确本阶段任务

开始编码前，先说明：

- 当前开发阶段。
- 本阶段目标。
- 需要完成的功能。
- 涉及的模块。
- 预计修改的文件。
- 依赖的已有模块。
- 可能存在的技术风险。

不能在没有明确任务范围的情况下直接修改大量代码。

## 5.2 第二步：分析现有代码

修改代码前必须：

1. 找到相关文件。
2. 阅读现有实现。
3. 检查相关接口。
4. 检查调用关系。
5. 检查依赖关系。
6. 确认是否存在可复用代码。
7. 确认是否需要调整已有实现。

不得在没有阅读现有代码的情况下直接重写模块。

## 5.3 第三步：设计本阶段实现方案

编码前明确：

- 模块职责。
- 数据结构。
- 接口定义。
- 前后端调用关系。
- 状态管理方式。
- 错误处理方式。
- 测试方式。

如果涉及数据库表结构修改，先明确 Migration。

如果涉及前后端接口修改，先明确请求和响应结构。

如果涉及技术依赖变化，先说明原因和影响。

## 5.4 第四步：实施编码

实施时遵循：

- 一个模块一个模块完成。
- 优先实现真实功能。
- 避免过度设计。
- 保持代码结构清晰。
- 复用已有公共能力。
- 避免重复实现相同逻辑。
- 及时处理编译错误。
- 及时处理类型错误。
- 不遗留明显的无效代码。

不要为了追求代码数量，一次性创建大量没有实际作用的文件。

## 5.5 第五步：执行测试

每次修改后，根据当前项目实际配置执行适用的检查。

前端：

- TypeScript 类型检查。
- ESLint。
- 单元测试。
- 前端构建。

Rust：

- `cargo fmt --check`。
- `cargo check`。
- `cargo clippy`。
- Rust 单元测试。

项目：

- Tauri 开发启动。
- Tauri 构建。
- 前后端 IPC 验证。
- 相关集成测试。

具体命令应以项目实际配置为准。

如果某项命令不存在，应说明原因，不得将未执行的测试标记为通过。

## 5.6 第六步：检查本阶段交付物

完成后核对：

- 功能是否完成。
- 代码是否编译。
- 测试是否通过。
- 是否有未处理错误。
- 是否影响已有功能。
- 是否符合设计文档。
- 是否需要更新技术文档。
- 是否存在遗留问题。

## 5.7 第七步：向用户汇报

完成当前阶段后，必须输出阶段报告。

报告格式见第十章。

在用户确认后，再进入下一阶段。

# 六、代码质量与工程规范

## 6.1 代码组织

遵循：

```
docs/07-项目目录结构与代码规范.md
```

要求：

- Vue 组件职责清晰。
- Store 不承担复杂业务执行逻辑。
- Composable 负责可复用的前端逻辑。
- Rust Command 负责 IPC 参数接收和结果返回。
- Service 负责业务编排。
- Repository 负责本地持久化。
- Adapter 负责具体数据源实现。

不得将所有业务逻辑写入一个 Vue 页面或一个 Rust 文件。

## 6.2 类型规范

前后端接口必须尽量保持类型一致。

前端 TypeScript 类型不能只为了消除报错而使用大量 `any`。

Rust 不得无理由大量使用 `unwrap()` 和 `expect()` 处理业务输入或外部资源错误。

需要明确处理：

- 空值。
- 网络异常。
- 数据库异常。
- 类型转换异常。
- 连接失效。
- 任务取消。
- 权限错误。

## 6.3 错误处理

错误信息应具备可读性。

建议区分：

- 参数错误。
- 配置错误。
- 凭据错误。
- 连接错误。
- SQL 语法错误。
- SQL 执行错误。
- 数据读取错误。
- 权限错误。
- 任务取消。
- 内部错误。

前端不得只显示“操作失败”。

同时也不得向用户暴露不必要的密码、凭据或敏感连接信息。

## 6.4 日志规范

日志应包含必要的上下文：

- 模块。
- 操作类型。
- 数据源 ID。
- 任务 ID。
- 错误类型。
- 错误原因。

不得记录：

- 数据库密码。
- 完整凭据内容。
- 不必要的敏感 SQL 参数。
- 其他不应进入普通日志的敏感数据。

## 6.5 性能规范

重点关注：

- 大结果集读取。
- 多任务并发。
- IPC 数据传输。
- 大字段展示。
- 前端表格渲染。
- 连接池管理。
- 任务清理。
- 内存释放。

不得将大量查询结果一次性传输给前端。

需要根据结果规模采用流式读取、分批传输或分页读取。

# 七、安全与数据操作约束

## 7.1 禁止使用生产数据库进行开发测试

不得默认连接生产数据库进行测试。

测试必须使用：

- 本地 MySQL。
- 专门的测试数据库。
- 明确授权的测试环境。

没有用户授权时，不得执行真实数据库写入操作。

## 7.2 危险操作必须确认

对于以下操作，应设置明确的用户确认机制：

- 删除表。
- 删除数据库。
- 批量删除数据。
- 批量更新数据。
- 执行可能造成大量数据变更的 SQL。
- 其他具有明显破坏性的操作。

不得为了方便开发而绕过产品中的安全确认。

## 7.3 SQL 安全

必须：

- 参数化处理 SQL 值。
- 验证动态标识符。
- 防止筛选和排序条件注入。
- 明确执行目标数据源。
- 明确当前数据库上下文。
- 隔离不同标签页的执行状态。

不能将前端传来的任意字符串未经检查就拼接到数据浏览器生成的 SQL 中。

注意：用户在 SQL 编辑器中主动输入并执行的任意 SQL，与程序自动生成的查询 SQL 是两种不同的场景，不能混淆。

# 八、依赖管理与技术决策

## 8.1 依赖选择

技术栈中已经确定的核心技术不得随意替换。

对于尚未最终确认的依赖，应先进行技术验证。

例如：

- MySQL 驱动。
- SQL 解析库。
- Monaco Editor 集成方案。
- CSV 导出库。
- 系统凭据管理库。
- SQLite 访问方案。

## 8.2 新增依赖

新增依赖前必须说明：

1. 为什么需要。
2. 解决什么问题。
3. 是否存在已有依赖可以实现。
4. 是否影响跨平台构建。
5. 是否引入额外维护成本。
6. 是否存在许可证或安全风险。

未经分析不得随意引入大量依赖。

## 8.3 依赖升级

不得在没有明确原因的情况下升级所有依赖。

升级前应检查：

- 当前版本。
- 兼容性。
- 破坏性变更。
- Tauri 兼容性。
- Rust 版本要求。
- 前端构建兼容性。

依赖升级后必须重新执行相关测试。

## 8.4 技术验证记录

对于影响架构的重要技术决策，应记录：

- 问题背景。
- 候选方案。
- 验证过程。
- 验证结果。
- 最终选择。
- 选择原因。
- 未解决的问题。

可以在 `docs/技术决策记录.md` 中维护。

不得在未经验证的情况下将临时方案当作最终架构。

# 九、设计文档维护规范

设计文档是项目开发的长期依据。

代码和设计文档必须保持一致。

出现以下情况时，应同步更新文档：

- 前后端接口发生变化。
- SQLite 表结构发生变化。
- Rust 模块职责发生变化。
- 数据源适配器接口发生变化。
- 关键依赖发生变化。
- 开发计划发生变化。
- 某项功能的实现方式发生变化。

如果实际开发中发现原设计不可行：

1. 说明原设计存在的问题。
2. 给出实际验证结果。
3. 提出替代方案。
4. 说明对现有模块的影响。
5. 等待必要的用户确认。
6. 确认后更新对应文档。
7. 再按照更新后的设计实施。

不得只修改代码而不更新对应设计文档。

- 修复实际问题。
- 重新执行失败的测试。
- 检查是否引入新的问题。

不得通过删除测试、屏蔽错误或降低检查标准来制造通过结果。

## 11.4 遇到无法解决的问题

如果当前阶段存在无法解决的问题，应：

- 保留已完成的有效代码。
- 记录失败原因。
- 记录尝试过的方案。
- 说明是否影响后续开发。
- 给出需要用户处理的事项。

不能为了继续开发而隐藏问题。

# 十四、AI 开发工具最终执行指令

在开始开发 DataDock 时，请始终遵循以下执行原则：

**第一：先阅读全部设计文档。**

理解产品定位、技术架构、UI 设计、数据库设计、核心模块和测试标准。

**第二：先检查现有项目。**

不要假设项目是空目录，不要覆盖已有代码。

**第三：严格按照开发阶段推进。**

先建立可运行的基础项目，再逐步实现真实功能。

**第四：每次只完成一个明确阶段。**

不要一次性生成所有模块，也不要在当前阶段尚未通过验证时直接进入后续阶段。

**第五：优先实现真实功能。**

不要使用大量 Mock 数据、空接口或假操作来制造完成效果。

**第六：重视安全和数据准确性。**

尤其是数据库密码、SQL 执行、数据修改、任务取消和多连接隔离。

**第七：每次修改都必须进行验证。**

能编译、能启动、能测试，才算具备阶段交付条件。

**第八：保持设计文档与代码一致。**

出现技术变化时，及时更新相关文档和技术决策记录。

**第九：维护开发状态。**

确保即使更换 AI 会话或编码工具，也能够根据项目状态文件继续工作。

**第十：每个阶段完成后向用户汇报。**

说明实际完成内容、修改文件、测试结果、遗留问题和下一步计划。

# 十五、首次启动开发时的执行要求

当收到 DataDock 项目开发任务时，第一次不要直接开始编写业务功能。

请按以下顺序执行：

1. 检查项目根目录。
2. 检查 `docs` 文件夹。
3. 完整读取 `docs/00` 至 `docs/12` 的设计文档。
4. 检查现有 Git 状态。
5. 检查现有项目结构。
6. 检查开发环境。
7. 整理项目技术约束。
8. 检查是否存在需要确认的技术问题。
9. 创建或更新 `docs/AI开发状态.md`。
10. 输出项目检查报告。
11. 根据 `docs/08-开发实施计划与里程碑.md` 确定第一阶段任务。
12. 等待用户确认后，开始第一阶段开发。

如果用户已经明确要求直接开始第一阶段，则不需要重复询问是否开始，可以在完成检查后直接实施。
