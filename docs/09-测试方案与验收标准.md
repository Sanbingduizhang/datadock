# DataDock 测试方案与验收标准

> 文档版本：V1.0
> 文档状态：测试规范
> 项目名称：DataDock
> 文档路径：`docs/09-测试方案与验收标准.md`

## 1. 文档目的

本文档用于规范 DataDock 的测试工作，明确测试范围、测试环境、测试数据、测试方法、测试用例及最终验收标准。

DataDock 是基于 Tauri 开发的桌面数据库管理工具，V1.0 主要支持 MySQL 数据源。

由于 DataDock 涉及远程数据库连接、SQL 执行和数据修改，因此测试不仅需要验证界面是否正常，还需要重点验证：

1. 数据库连接是否可靠。
2. 数据库操作是否正确。
3. 多个数据源之间是否相互隔离。
4. SQL 执行是否会阻塞 UI。
5. 查询结果是否能够正确展示。
6. 数据新增、修改、删除是否安全。
7. 本地配置和密码是否得到妥善保护。
8. 网络异常和数据库异常是否能够正确处理。
9. 不同操作系统下应用是否能够正常运行。

测试的最终目标是保证 DataDock 不只是一个能够运行的界面，而是一个能够安全、稳定地执行数据库管理操作的桌面应用。

## 3.2 测试类型

测试分为以下几类：

### 单元测试

验证单个函数、服务或模块是否符合预期。

例如：

- 数据库配置校验。
- SQL 参数构造。
- 数据类型转换。
- 错误转换。
- 分页参数计算。
- 任务状态转换。

### 集成测试

验证多个模块协同工作是否正常。

例如：

- Rust Repository 与 SQLite。
- MySQL Adapter 与真实 MySQL。
- SQL 执行服务与任务管理器。
- Tauri Command 与前端。
- 系统凭据管理与连接管理。

### UI 测试

验证桌面应用界面和交互。

例如：

- 创建连接。
- 展开数据库。
- 打开 SQL 编辑器。
- 执行 SQL。
- 浏览表数据。
- 编辑表数据。

### 异常测试

验证异常场景下的系统表现。

例如：

- 数据库连接中断。
- SQL 执行失败。
- 权限不足。
- 数据库密码错误。
- SQLite 文件无法写入。

### 安全测试

验证系统是否存在明显的数据泄露和数据库操作风险。

例如：

- 密码是否明文保存。
- SQL 参数是否正确绑定。
- 动态排序字段是否经过校验。
- 删除操作是否具有安全保护。

### 性能测试

验证系统在一定数据量和并发操作下是否能够正常使用。

例如：

- 大结果集展示。
- 多连接执行 SQL。
- 大表分页。
- 大数据量导出。

# 5. 测试数据设计

## 5.1 基础测试表

建议创建一张用于基本 CRUD 测试的表：

```
CREATE TABLE test_users (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    username VARCHAR(100) NOT NULL,
    email VARCHAR(255),
    age INT,
    balance DECIMAL(12, 2),
    enabled TINYINT(1) DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username),
    KEY idx_email (email)
);
```

测试内容：

- 查询。
- 新增。
- 修改。
- 删除。
- 排序。
- 筛选。
- 分页。
- 主键定位。
- 唯一索引。

## 5.2 无主键测试表

```
CREATE TABLE test_no_primary_key (
    username VARCHAR(100),
    age INT,
    description TEXT
);
```

测试内容：

- 浏览数据。
- 查询数据。
- 编辑保护。
- 删除保护。
- 重复数据处理。

重点验证：

没有主键或可靠唯一键时，DataDock 不应使用不确定的条件修改或删除数据。

## 5.3 数据类型测试表

```
CREATE TABLE test_data_types (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tiny_value TINYINT,
    small_value SMALLINT,
    int_value INT,
    big_value BIGINT,
    decimal_value DECIMAL(20, 6),
    float_value FLOAT,
    double_value DOUBLE,
    char_value CHAR(20),
    varchar_value VARCHAR(255),
    text_value TEXT,
    long_text_value LONGTEXT,
    date_value DATE,
    time_value TIME,
    datetime_value DATETIME,
    timestamp_value TIMESTAMP,
    json_value JSON,
    binary_value VARBINARY(255),
    blob_value BLOB,
    nullable_value VARCHAR(100),
    PRIMARY KEY (id)
);
```

测试内容：

- 整数类型。
- 浮点类型。
- DECIMAL 精度。
- 字符串。
- 长文本。
- 日期时间。
- JSON。
- 二进制。
- NULL。

特别注意：

DECIMAL 不应因为前后端数值转换而丢失精度。

BIGINT UNSIGNED 超出 JavaScript 安全整数范围时，必须采用安全的数据表示方式，不能直接转换为普通 JavaScript Number 后导致精度损失。

## 8.3 多连接测试

准备两个不同 MySQL 实例。

验证：

- 可以同时保存两个连接。
- 可以分别连接两个实例。
- 可以在两个连接之间切换。
- 可以同时执行查询。
- 一个连接断开不会影响另一个连接。
- 一个连接执行失败不会影响另一个连接。
- 删除一个连接不会错误删除另一个连接的凭据。

## 8.4 连接生命周期测试

重点测试：

1. 连接中重复点击连接按钮。
2. 连接过程中关闭窗口。
3. 已连接状态下重复连接。
4. 已断开状态下重复断开。
5. 数据库服务突然关闭。
6. 网络恢复后重新连接。
7. 删除正在使用的连接。

系统必须保持正确的连接状态，不能出现前端显示已连接但后端实际连接已经失效的情况。

## 8.5 连接管理验收标准

- 多连接配置互相隔离。
- 密码凭据与数据源正确关联。
- 连接状态真实可靠。
- 连接异常可以恢复。
- 连接释放正常。
- 不存在明显连接泄漏。

# 17. 安全测试

安全测试属于 P0，不能因为普通功能已经通过就跳过。

## 17.1 密码安全

检查：

- SQLite 中是否保存明文密码。
- 日志是否打印密码。
- 前端 Store 是否长期保存明文密码。
- 错误提示是否泄漏密码。
- 导出文件是否包含密码。
- 删除连接后凭据是否正确清理。

验收要求：

数据库密码只能通过系统凭据管理机制安全保存。

## 17.2 SQL 注入风险

重点检查：

- 动态排序字段。
- 动态筛选字段。
- 动态表名。
- 动态数据库名。
- 参数化查询。
- 用户输入的 SQL。

需要区分：

用户在 SQL 编辑器中主动输入并执行 SQL，是数据库客户端的正常能力。

但应用内部根据用户选择构造查询时，必须正确校验标识符并使用参数绑定。

## 17.3 数据修改安全

验证：

- 更新记录定位准确。
- 删除记录定位准确。
- 无主键表受到保护。
- 批量删除有确认。
- 筛选条件不会被错误拼接。
- 操作失败时不会显示虚假的成功状态。

## 17.4 本地数据安全

验证：

- 本地数据库文件位置合理。
- 凭据不存入普通配置文件。
- 日志不包含敏感内容。
- 本地历史记录不会意外上传。
- 不存在未经用户允许的网络数据传输。

## 17.5 安全验收标准

不存在已知的严重凭据泄露问题。

内部构造的 SQL 查询采用安全的参数处理方式。

重要数据修改操作具备必要的保护机制。

具体命令以项目实际配置为准。

常见检查示例：


最终验收不能只依赖 AI 对代码的自我判断。

涉及真实数据库操作的功能，必须通过实际 MySQL 测试环境验证。

## 25. 最终测试原则

DataDock 是数据库管理工具，正确性和安全性优先于功能数量。

测试过程中必须特别关注：

- 不能错误修改数据。
- 不能错误删除数据。
- 不能混淆不同数据库连接。
- 不能泄漏数据库密码。
- 不能将客户端取消误报为服务端取消。
- 不能将未经验证的功能描述为已经支持。
- 不能用 UI 演示代替真实数据库测试。

**最终验收标准：功能真实可用、数据操作正确、异常处理可靠、凭据安全、核心体验稳定。**
