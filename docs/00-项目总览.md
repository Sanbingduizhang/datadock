# DataDock 项目总览

## 1. 项目背景

在日常软件开发过程中，开发者经常需要使用不同的数据库和数据服务。

例如：

- 使用 MySQL 存储业务数据。
- 使用 Redis 处理缓存和临时数据。
- 使用 PostgreSQL 存储结构化业务数据。

在开发过程中，开发者通常需要使用不同的客户端工具管理这些服务。

当需要频繁切换数据库、查看数据、执行 SQL、修改表结构或排查数据问题时，多个工具之间的切换会增加操作成本。

DataDock 希望通过一个统一的桌面工作台解决这一问题。

用户只需要安装一个应用，就可以逐步实现对多种数据源的连接、浏览、查询和管理。

## 2. 产品定位

DataDock 是一款面向软件开发者的轻量级跨平台多数据源管理工具。

产品定位：

**一个桌面应用，统一管理多种数据源。**

核心理念：

- 轻量化：尽量减少应用资源占用，避免不必要的复杂功能。
- 统一化：不同类型的数据源使用统一的应用入口和交互体系。
- 专业化：采用符合程序员使用习惯的 IDE 风格界面。
- 模块化：每种数据源采用独立适配器，降低模块之间的耦合。
- 本地化：默认本地运行，用户数据保存在本地。
- 可扩展：支持后续增加新的数据库类型和数据服务。

## 3. 产品目标

### 3.1 核心目标

DataDock 首先解决开发者日常数据库管理需求。

包括：

1. 统一管理数据库连接。
2. 快速连接和断开数据库。
3. 浏览数据库对象。
4. 查询和查看数据。
5. 编辑和维护数据。
6. 查看数据库表结构。
7. 提供方便的 SQL 编辑和执行环境。
8. 管理多个数据库连接。
9. 保存常用查询和查询历史。

### 3.2 长期目标

随着版本迭代，逐步支持不同类型的数据服务。

最终形成统一的数据管理工作台，而不是仅仅作为一个 MySQL 客户端。

## 4. 目标用户

主要面向以下用户：

### 4.1 后端开发工程师

日常需要查看业务数据、执行 SQL、修改数据、排查问题。

### 4.2 全栈开发工程师

需要同时管理多种数据库和数据服务。

### 4.3 数据库开发人员

需要进行数据库结构查看、数据查询和基础维护。

### 4.4 个人开发者

希望使用一个轻量级工具管理个人项目中的数据库。

## 5. 产品核心模块

DataDock 从产品层面划分为以下模块。

### 5.1 数据源管理

负责管理用户配置的各种数据源。

主要功能：

- 新建数据源。
- 编辑数据源。
- 删除数据源。
- 测试连接。
- 建立连接。
- 断开连接。
- 保存连接配置。
- 管理多个连接。
- 按名称搜索连接。
- 对连接进行分组。
- 显示连接状态。

数据源管理模块不直接负责具体数据库业务操作，而是负责数据源配置和生命周期管理。

### 5.2 数据源资源管理器

负责展示已经建立连接的数据源及其内部资源。

MySQL 资源结构示例：

```
MySQL Connection
├── 数据库 A
│   ├── Tables
│   │   ├── users
│   │   ├── orders
│   │   └── products
│   ├── Views
│   ├── Functions
│   └── Procedures
│
└── 数据库 B
    ├── Tables
    └── Views
```

Redis 和 PostgreSQL 根据各自数据模型提供对应的资源浏览方式。

### 5.3 SQL 编辑器

提供数据库查询和开发环境。

主要功能：

- SQL 编辑。
- SQL 语法高亮。
- SQL 关键字提示。
- SQL 执行。
- SQL 执行结果展示。
- 多编辑器标签页。
- SQL 格式化。
- 执行时间展示。
- 执行错误提示。
- 查询历史。
- SQL 文件打开与保存。

SQL 编辑器是 V1 的核心功能之一。

### 5.4 数据浏览器

负责查看和维护数据库中的数据。

主要功能：

- 查看表数据。
- 分页查询。
- 排序。
- 条件筛选。
- 搜索。
- 新增数据。
- 编辑数据。
- 删除数据。
- 复制单元格内容。
- 导出查询结果。

具体功能按照不同数据源的能力分别实现。

### 5.5 数据库结构管理

负责查看数据库结构信息。

MySQL 主要包括：

- 数据库列表。
- 表列表。
- 视图列表。
- 表字段。
- 字段类型。
- 字段长度。
- 是否允许 NULL。
- 默认值。
- 主键。
- 索引。
- 自增属性。
- 表引擎。
- 表注释。

后续版本根据 Redis、PostgreSQL 的数据模型提供相应功能。

### 5.6 查询历史

记录用户执行过的查询操作。

主要功能：

- 记录 SQL。
- 记录所属连接。
- 记录执行时间。
- 记录执行状态。
- 记录执行耗时。
- 查看历史记录。
- 重新执行历史 SQL。

查询历史默认保存在本地。

敏感 SQL 参数应避免被不必要地记录。

### 5.7 应用设置

管理 DataDock 自身配置。

主要功能：

- 深色主题。
- 浅色主题。
- 跟随系统主题。
- 编辑器字体。
- 编辑器字号。
- 自动保存相关配置。
- 查询结果展示配置。
- 数据源连接配置。
- 应用基础设置。

- 自动执行未经用户确认的数据修改操作。

## 7. 核心使用流程

### 7.1 首次使用

1. 用户启动 DataDock。
2. 进入主界面。
3. 创建 MySQL 数据源。
4. 填写数据库连接信息。
5. 测试连接。
6. 保存连接配置。
7. 建立数据库连接。
8. 在左侧资源管理器查看数据库和表。

### 7.2 数据浏览流程

1. 用户选择一个数据库。
2. 展开 Tables。
3. 选择需要查看的表。
4. 打开数据浏览标签页。
5. 查询表数据。
6. 通过分页、排序和筛选查找数据。
7. 根据需要进行新增、编辑或删除。

### 7.3 SQL 查询流程

1. 用户选择一个 MySQL 连接。
2. 打开 SQL 编辑器。
3. 编写 SQL。
4. 选择执行范围。
5. 执行 SQL。
6. 后端负责执行查询。
7. 前端展示查询结果。
8. 保存查询历史。

### 7.4 多连接管理流程

1. 用户创建多个数据库连接。
2. 左侧资源管理器显示所有连接。
3. 用户可以分别连接不同数据库。
4. 每个连接拥有独立的连接状态。
5. 不同连接的查询和结果相互隔离。
6. 用户可以在多个连接之间切换。

## 8. 产品界面总体规划

DataDock 采用 IDE 风格工作台。

主要区域：

### 顶部工具栏

负责全局操作。

包括：

- 应用菜单。
- 新建连接。
- 打开 SQL 编辑器。
- 保存操作。
- 主题切换。
- 设置入口。

### 左侧资源管理区域

负责数据源和数据库对象展示。

包括：

- 数据源连接列表。
- 连接分组。
- 数据库列表。
- 表列表。
- 视图列表。

### 中央工作区域

负责主要业务操作。

包括：

- SQL 编辑器。
- 数据浏览器。
- 表结构查看。
- 查询结果。
- 多标签页。

### 底部信息区域

负责展示操作状态。

包括：

- SQL 执行消息。
- 执行时间。
- 影响行数。
- 错误信息。
- 应用运行状态。

具体界面以 UI 与交互设计规范为准。

## 9. 数据与运行模式

DataDock 默认采用本地运行模式。

### 9.1 本地配置

用户的以下数据默认保存在本地：

- 数据源配置。
- 用户界面设置。
- 查询历史。
- 收藏的 SQL。
- 应用偏好设置。

### 9.2 数据库数据

DataDock 不默认将用户的整个数据库复制到本地。

用户查询的数据只在必要时传输到应用界面，并根据结果集限制进行加载。

### 9.3 远程数据库

DataDock 可以连接用户自己部署的远程数据库。

连接过程由本地应用发起，不需要依赖 DataDock 官方服务器。

### 9.4 云端同步

第一阶段不实现云端同步。

后续如果有需要，可以考虑增加可选的配置同步能力。

云端同步不能成为应用正常工作的必要条件。

## 10. 多数据源扩展规划

DataDock 采用统一入口、独立适配器的设计思路。

不同数据源共享应用层面的通用能力，但具体数据操作由各自适配器实现。

### MySQL

主要提供：

- SQL 查询。
- 数据库对象浏览。
- 表数据操作。
- 表结构查看。

### Redis

主要提供：

- Key 管理。
- Value 查看。
- 数据类型识别。
- TTL 管理。
- Redis 命令执行。

### PostgreSQL

主要提供：

- SQL 查询。
- Schema 管理。
- 表数据操作。
- 表结构查看。
- 索引与约束查看。

不同数据源不应强制使用不符合自身数据模型的统一操作方式。

## 11. 非功能性需求

### 11.1 性能

- 应用启动应尽量快速。
- 界面交互应保持流畅。
- 数据库连接不能阻塞 UI 线程。
- 大量数据应采用分页或分批加载。
- 多个连接之间应相互隔离。
- 长时间运行的任务应能够反馈运行状态。

### 11.2 稳定性

- 数据库断开后应能够识别连接失效。
- 数据库连接失败应提供明确错误。
- 查询失败不得导致整个应用崩溃。
- 长时间查询应支持取消。
- 单个数据源异常不得影响其他数据源。

### 11.3 安全性

- 密码不能明文存储。
- 连接配置需要安全管理。
- 数据修改操作需要必要的确认。
- 不得未经用户操作自动执行 SQL。
- 不得向外部服务器上传数据库数据。

### 11.4 跨平台

目标支持：

- macOS
- Windows
- Linux

不同平台可能存在系统安全凭据存储和打包方式的差异，需要分别验证。

## 12. 项目成功标准

V1.0 达到以下条件，可以认为第一阶段完成：

1. 能够正常创建和管理 MySQL 连接。
2. 能够连接常见版本的 MySQL 服务。
3. 能够浏览数据库和表。
4. 能够使用 SQL 编辑器执行查询。
5. 能够正确展示查询结果。
6. 能够浏览和编辑表数据。
7. 能够查看表结构和索引。
8. 能够管理多个数据库连接。
9. 能够保存本地连接配置。
10. 能够安全保存数据库凭据。
11. 应用能够在目标操作系统正常运行。
12. 核心功能经过实际测试。

## 13. 后续产品演进

DataDock 不以功能数量作为唯一发展目标。

后续版本应优先考虑：

- 多数据源管理体验。
- 数据浏览效率。
- SQL 编辑体验。
- 连接管理体验。
- 应用稳定性。
- 资源占用。
- 数据安全。

每个版本都应该在已有功能稳定的基础上进行扩展。

**最终目标：让 DataDock 成为开发者日常开发过程中一个轻量、可靠、顺手的数据管理工作台。**
