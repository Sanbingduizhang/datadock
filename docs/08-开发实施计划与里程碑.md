## 1. 文档目的

本文档用于指导 DataDock V1.0 的实际开发工作，明确项目开发阶段、实施顺序、阶段任务、交付物、验收标准和里程碑。

DataDock 采用 Tauri 桌面应用架构，前端负责 UI 和交互，Rust 后端负责本地数据管理、数据库连接、SQL 执行及数据源适配。

开发过程中必须遵循以下原则：

1. 先完成项目基础框架，再逐步实现业务功能。
2. 优先验证存在技术不确定性的核心能力。
3. 每个阶段必须有明确的交付物和验收标准。
4. 当前阶段未通过验收，不得直接进入依赖该阶段的后续开发。
5. 不得为了追求开发速度而忽略架构设计和安全要求。
6. 不得擅自增加产品需求文档之外的功能。
7. 技术选型中尚未确定的内容，必须先通过技术验证再确定。
8. 开发过程中发现设计问题，应先更新相关文档，再修改代码。

## 2. V1.0 开发目标

### 2.1 核心目标

完成一个能够正常使用的跨平台桌面数据库管理工具。

V1.0 以 MySQL 为首个数据源，实现数据库连接、资源管理、SQL 编辑、SQL 执行、数据浏览、数据编辑和本地历史管理等核心能力。

### 2.2 V1.0 必须实现的功能

| 模块       | 功能                         | 优先级 |
| ---------- | ---------------------------- | ------ |
| 桌面框架   | Tauri 桌面应用基础框架       | P0     |
| 主界面     | Navicat 风格主界面布局       | P0     |
| 主题       | 深色、浅色、跟随系统         | P0     |
| 连接管理   | MySQL 连接新增、编辑、删除   | P0     |
| 连接管理   | 连接测试、连接、断开         | P0     |
| 资源管理   | 数据库、表、视图资源树       | P0     |
| SQL 编辑器 | SQL 编辑、高亮、基本编辑能力 | P0     |
| SQL 执行   | 当前语句、选中内容、全部执行 | P0     |
| 查询结果   | 查询结果展示                 | P0     |
| 数据浏览器 | 表数据分页、排序、筛选       | P0     |
| 数据浏览器 | 数据新增、修改、删除         | P0     |
| 表结构     | 字段、索引、建表 SQL 查看    | P0     |
| 本地存储   | SQLite 本地数据管理          | P0     |
| 安全       | 数据库密码安全保存           | P0     |
| 查询历史   | SQL 执行历史记录             | P1     |
| SQL 收藏   | SQL 收藏和管理               | P1     |
| 数据导出   | CSV、JSON 导出               | P1     |
| 设置       | 编辑器和结果展示设置         | P1     |

P0 是 V1.0 核心交付要求。

P1 应尽量在 V1.0 中完成，但不能因为 P1 功能影响核心数据库操作能力。

### 2.3 V1.0 暂不实现的功能

以下功能不作为 V1.0 的必要交付内容：

- Redis 数据源。
- PostgreSQL 数据源。
- 云端账户体系。
- 云端配置同步。
- 数据库结构同步。
- 数据库迁移工具。
- ER 图。
- SSH 隧道。
- 高级数据库备份和恢复。
- 数据库服务器监控。
- 多人协作。
- 插件市场。
- AI SQL 助手。

后续可以根据产品发展逐步加入。

# 4. 阶段 0：项目初始化与技术验证

## 4.1 阶段目标

建立 DataDock 的基础开发环境，验证核心技术组件是否能够满足产品需求。

本阶段不追求完整业务功能，重点是解决技术选型和基础能力的不确定性。

尤其需要验证：

- Tauri 与 Vue 3 的集成。
- 前端与 Rust 后端 IPC 通信。
- Rust 连接 MySQL。
- Rust 操作本地 SQLite。
- Monaco Editor 在 Tauri 中的运行。
- 数据库密码的系统凭据保存能力。
- SQL 驱动是否满足数据库客户端的使用场景。

## 4.2 具体开发任务

### 任务 0.1：初始化项目

建立项目基础目录。

建议采用：

```
DataDock/
├── src/
├── src-tauri/
├── docs/
├── package.json
├── vite.config.ts
├── tsconfig.json
├── index.html
└── README.md
```

具体目录应遵循：

```
07-项目目录结构与代码规范.md
```

需要完成：

- 初始化 Tauri 项目。
- 初始化 Vue 3 项目。
- 配置 TypeScript。
- 配置 Vite。
- 配置前端代码检查。
- 配置 Rust 项目。
- 建立 Git 仓库。
- 配置 `.gitignore`。
- 确认本地开发启动流程。

### 任务 0.2：验证 Tauri IPC

建立一个最小 Rust Command。

前端调用 Rust Command，Rust 返回测试数据。

验证：

- 前端能够调用 Rust。
- Rust 能够接收参数。
- Rust 能够返回结构化数据。
- Rust 错误能够正确返回前端。
- 不同 Command 可以正常注册和调用。

交付要求：

建立一个完整的前后端调用示例，作为后续 Command 开发的基础。

### 任务 0.3：验证 SQLite

使用 Rust 访问本地 SQLite 数据库。

验证：

- 创建数据库文件。
- 创建数据表。
- 插入数据。
- 查询数据。
- 修改数据。
- 删除数据。
- 事务处理。
- 数据库迁移能力。

如果最终采用 SQLx，需要验证 SQLx 与当前 Rust、Tauri 版本的兼容性。

### 任务 0.4：验证 MySQL 驱动

这是本阶段最重要的技术验证任务之一。

不能仅仅验证能否连接 MySQL，还需要验证驱动是否适合数据库客户端的真实使用场景。

至少验证以下能力：

| 验证项目 | 验证要求                        |
| -------- | ------------------------------- |
| 连接     | 能够连接 MySQL 服务             |
| 认证     | 支持常见 MySQL 认证方式         |
| 查询     | 能够执行 SELECT                 |
| 更新     | 能够执行 INSERT、UPDATE、DELETE |
| DDL      | 能够执行 CREATE、ALTER、DROP    |
| 多语句   | 验证多语句执行能力              |
| 多结果集 | 验证驱动能否读取多个结果集      |
| 类型映射 | 能够处理常见 MySQL 字段类型     |
| NULL     | 能够正确处理 NULL               |
| 大字段   | 验证 TEXT、BLOB 等字段          |
| 事务     | 支持事务提交和回滚              |
| 错误     | 能够获取数据库错误信息          |
| 连接池   | 能够管理多个连接                |
| 超时     | 能够处理连接和查询超时          |
| 取消     | 验证查询取消能力及其真实语义    |

特别注意：

SQLx 可以作为候选方案，但不能因为架构文档中提到了 SQLx，就直接认定它已经满足全部需求。

如果 SQLx 无法满足多语句、多结果集或其他核心客户端能力，应重新评估驱动方案。

不能为了坚持某个技术选型而削弱产品功能。

### 任务 0.5：验证 Monaco Editor

将 Monaco Editor 集成到 Vue 页面中。

验证：

- 编辑器初始化。
- SQL 语法高亮。
- 行号。
- 代码缩进。
- 括号匹配。
- 查找和替换。
- 多编辑器实例。
- 主题切换。
- Tauri 打包环境中的资源加载。

### 任务 0.6：验证系统凭据管理

验证不同操作系统下的凭据保存能力。

目标：

- macOS：Keychain。
- Windows：Credential Manager。
- Linux：Secret Service 或其他适合的系统凭据方案。

验证：

1. 保存数据库密码。
2. 根据凭据引用读取密码。
3. 删除凭据。
4. 应用重启后仍然可以读取。
5. 不将明文密码写入 SQLite。
6. 不将明文密码写入普通日志。

如果某个平台的系统凭据能力存在依赖或限制，需要记录清楚。

### 任务 0.7：验证大数据传输

通过 Tauri IPC 将 MySQL 查询结果返回前端。

重点观察：

- 数据量较大时的传输速度。
- 前端内存占用。
- Rust 内存占用。
- 数据序列化开销。
- 大字段传输表现。

需要根据实际测试结果确定查询结果的分页和批量传输策略。

不能直接将大量数据库结果一次性传输到前端。

# 6. 阶段 2：本地 SQLite 与连接管理

## 6.1 阶段目标

实现本地数据持久化和 MySQL 数据源连接管理。

完成后，用户可以添加多个 MySQL 连接，并在应用重启后恢复连接配置。

## 6.2 具体开发任务

### 任务 2.1：初始化本地 SQLite

实现：

- 获取系统应用数据目录。
- 创建 SQLite 数据库文件。
- 数据库连接初始化。
- 数据库连接池或连接管理。
- 数据库表创建。
- Migration 机制。
- 本地数据访问 Repository。

本地数据库至少需要支持：

- data_sources。
- query_history。
- sql_favorites。
- app_settings。
- workspace_state。

实际表结构遵循：

```
04-数据库设计.md
```

### 任务 2.2：实现数据源配置管理

实现数据源配置 CRUD：

- 新增数据源。
- 查询数据源列表。
- 修改数据源。
- 删除数据源。
- 获取数据源详情。

连接配置包括：

- 连接名称。
- 主机地址。
- 端口。
- 用户名。
- 密码凭据引用。
- 默认数据库。
- 连接超时时间。
- 其他必要连接参数。

### 任务 2.3：实现密码安全保存

实现：

- 保存密码到系统凭据管理服务。
- 获取密码。
- 更新密码。
- 删除密码。

SQLite 只保存凭据引用。

任何业务 Command 都不能将明文密码返回前端作为普通连接配置的一部分。

### 任务 2.4：实现连接测试

连接测试需要：

1. 获取连接配置。
2. 根据凭据引用读取密码。
3. 创建临时数据库连接。
4. 执行简单连接验证。
5. 返回成功或失败信息。
6. 释放临时连接资源。

连接测试不应永久占用连接池资源。

### 任务 2.5：实现连接生命周期管理

实现：

- 建立数据库连接。
- 断开数据库连接。
- 查询连接状态。
- 获取当前连接信息。
- 多连接管理。
- 应用退出时释放连接。

连接状态建议：

```
disconnected
connecting
connected
disconnecting
error
```

需要避免同一个数据源重复创建不必要的连接池。

### 任务 2.6：实现连接管理 UI

实现连接列表和连接编辑弹窗。

支持：

- 新建连接。
- 编辑连接。
- 删除连接。
- 测试连接。
- 连接数据库。
- 断开连接。
- 显示连接状态。

### 任务 2.7：实现连接状态同步

Rust 后端负责维护真实连接状态。

前端 Store 负责展示状态。

不能仅通过前端按钮点击就认为连接成功，必须以 Rust 后端实际连接结果为准。

### 任务 4.3：实现 SQL 执行范围识别

支持三种执行模式：

1. 执行当前语句。
2. 执行选中 SQL。
3. 执行全部 SQL。

需要正确处理：

- 分号。
- 多行 SQL。
- 注释。

不能简单使用字符串 `split(';')` 实现完整 SQL 语句拆分。

如果采用 SQL 解析器，需要评估其对 MySQL 语法和客户端执行场景的支持程度。

### 任务 4.4：实现 SQL 异步执行

Rust 后端负责实际 SQL 执行。

每次执行任务需要具备独立的任务标识。

建议结构：

```
task_id
connection_id
workspace_id
sql
status
start_time
end_time
```

执行流程：

```
前端发起执行请求
        |
        v
Rust 接收请求
        |
        v
创建执行任务
        |
        v
返回 task_id
        |
        v
异步执行 SQL
        |
        v
获取查询结果
        |
        v
返回结果或发送执行事件
        |
        v
前端更新执行状态
```

任务状态建议：

```
pending
running
success
failed
cancelled
```


- SQL 执行位置。
- 执行耗时。

错误信息不能只返回一个模糊的“执行失败”。

### 任务 4.8：实现 SQL 任务取消

提供取消执行入口。

必须区分：

- 前端停止等待结果。
- Rust 任务停止后续处理。
- 数据库驱动取消当前请求。
- MySQL 服务端真正停止执行。

只有驱动或数据库协议层确认支持时，才能宣称实现了服务端查询取消。

如果暂时不支持，应明确展示取消能力限制。

### 任务 4.9：实现连接隔离

SQL 任务必须绑定明确的连接。

不同连接之间不能混用数据库会话。

多个 SQL 工作区之间不能错误共享执行状态。

# 13. 关键技术风险与验证要求

## 13.1 MySQL 驱动能力

风险：

普通数据库驱动可能不具备完整数据库客户端所需要的能力。

必须验证：

- 多语句执行。
- 多结果集。
- MySQL 类型映射。
- 事务。
- 取消语义。
- 连接管理。
- 错误信息。

处理方式：

在阶段 0 完成技术验证。

如果不满足需求，先调整驱动方案。

## 13.2 SQL 执行取消

风险：

取消 Rust 异步任务，不代表 MySQL 服务端停止执行 SQL。

处理方式：

明确区分客户端任务取消和数据库服务端取消。

根据驱动支持情况决定具体实现。

## 13.3 系统凭据管理

风险：

不同操作系统凭据管理机制存在差异。

处理方式：

通过独立 CredentialManager 封装系统凭据能力。

不得在业务模块中直接依赖某个平台的实现细节。

## 13.4 Tauri IPC 大数据传输

风险：

查询结果较大时，IPC 序列化和数据传输可能产生明显开销。

处理方式：

- 限制单次返回数据量。
- 使用分页或分批获取。
- 控制大字段传输。
- 避免一次性返回全部结果。
- 必要时评估基于任务 ID 的分批读取方案。

## 13.5 MySQL 版本兼容

风险：

不同 MySQL 版本在系统表、权限和部分语法方面可能存在差异。

处理方式：

至少选择实际目标版本进行验证。

如果计划兼容 MySQL 5.7、8.0 等不同版本，需要明确记录各版本支持范围，并进行对应测试。

不要默认所有版本的元数据查询都完全一致。

## 13.6 SQLite 数据迁移

风险：

开发过程中本地 SQLite 表结构可能持续变化。

处理方式：

- 使用版本化 Migration。
- 禁止直接删除用户数据库文件解决迁移问题。
- 对重要数据迁移前做好保护。
- 测试旧版本数据升级到新版本的过程。

## 13.7 数据修改安全

风险：

数据浏览器中的错误更新和删除可能造成用户数据损失。

处理方式：

- 优先使用主键定位。
- 无主键表采取保护措施。
- 删除操作增加确认。
- 筛选条件采用参数化处理。
- 对可能影响多行的操作进行明确提示。

# 16. AI 开发执行规范

DataDock 预计采用 AI 辅助开发，因此需要对 AI 的开发行为进行约束。

## 16.1 开发前必须阅读文档

每次开始开发前，AI 必须先阅读：

- 项目总览。
- 产品需求。
- UI 设计规范。
- 技术架构。
- 数据库设计。
- 核心模块设计。
- 前后端接口设计。
- 项目目录和代码规范。
- 当前开发实施计划。

根据当前任务，只需要重点阅读相关章节，但不能忽略已经确定的架构约束。

## 16.2 一次只执行一个明确任务

不允许一次性要求 AI 完成整个阶段的所有功能。

应拆分成独立任务。

例如：

```
阶段 2：本地 SQLite 与连接管理

任务 2.1：初始化 SQLite
任务 2.2：实现数据源 Repository
任务 2.3：实现凭据管理
任务 2.4：实现连接测试
任务 2.5：实现连接生命周期
任务 2.6：实现连接管理 UI
```

每个任务单独实施和验收。

## 16.3 编码前输出实施计划

开始修改代码前，AI 必须先明确：

1. 当前开发阶段。
2. 当前任务。
3. 任务目标。
4. 涉及的文件。
5. 需要新增的文件。
6. 需要修改的文件。
7. 是否涉及数据库结构变化。
8. 是否涉及接口变化。
9. 可能存在的风险。
10. 测试方案。

如果任务涉及架构变化，必须先说明原因和影响。

## 16.4 禁止擅自扩大任务范围

AI 不得：

- 擅自增加新业务功能。
- 擅自修改已经确定的技术架构。
- 擅自替换已经确认的依赖。
- 擅自删除已有功能。
- 为了方便开发而绕过安全设计。
- 在没有说明的情况下修改数据库结构。
- 在没有确认的情况下改变前后端接口。

如果发现原设计无法实现，应先提出问题和调整建议。

## 16.5 完成编码后必须测试

每次任务完成后，AI 必须说明：

- 修改了哪些文件。
- 新增了哪些功能。
- 使用了哪些接口。
- 执行了哪些测试。
- 测试结果。
- 已知问题。
- 是否满足当前任务验收标准。

不能仅仅回复“代码已经完成”。

## 16.6 同步维护文档

如果开发过程中发生以下变化，需要同步更新文档：

- 技术选型变化。
- 数据库结构变化。
- Command 接口变化。
- 模块职责变化。
- 项目目录变化。
- 产品需求变化。

文档必须反映实际实现，不得出现文档和代码长期不一致的情况。

## 16.7 技术验证失败时的处理

如果当前任务依赖的技术能力没有通过验证：

1. 停止依赖该能力的后续开发。
2. 记录失败现象。
3. 分析失败原因。
4. 提出替代方案。
5. 对替代方案进行验证。
6. 更新技术架构文档。
7. 重新确认实施计划。

禁止通过临时绕过、硬编码或隐藏错误的方式让任务表面上通过。

# 19. 最终实施原则

DataDock 的开发应当遵循：

**先验证技术，再搭建架构；先完成核心能力，再完善辅助功能；先保证正确性，再优化使用体验。**

开发过程中，始终以产品需求文档和技术架构文档作为主要依据。

AI 的职责是按照已经确定的产品和技术方案完成具体开发，而不是在每次编码时重新设计整个项目。

当发现原有方案存在问题时，应先说明问题、分析影响、提出调整方案，再继续实施。

最终目标是交付一个真正可用、稳定、安全、具有良好扩展能力的桌面数据库管理工具，而不是仅仅完成一个能够运行的 UI 演示项目。
