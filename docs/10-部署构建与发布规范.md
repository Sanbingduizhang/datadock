# DataDock 部署构建与发布规范

> 文档版本：V1.0
> 文档状态：构建与发布规范
> 项目名称：DataDock
> 文档路径：`docs/10-部署构建与发布规范.md`

## 1. 文档目的

本文档用于规范 DataDock 的开发环境配置、桌面应用构建、安装包生成、版本管理和发布流程。

DataDock 基于 Tauri 开发，是一个跨平台桌面数据库管理工具。

V1.0 主要支持：

- macOS。
- Windows。

Linux 暂不作为 V1.0 必须发布的平台，是否支持根据后续实际开发情况确定。

本文档重点解决以下问题：

1. 开发人员如何搭建项目环境。
2. 如何启动本地开发版本。
3. 如何构建生产版本。
4. 如何生成不同操作系统的安装包。
5. 如何管理应用版本。
6. 如何处理本地配置和数据库文件。
7. 如何验证安装包。
8. 如何进行版本发布。
9. 如何处理应用升级。
10. 如何保证构建和发布过程可重复。

本文档不要求项目必须采用某个固定 CI/CD 平台。具体自动化方案可以根据实际开发环境选择。

# 2. 构建架构

## 2.1 整体架构

DataDock 使用 Tauri 桌面应用架构。

```
DataDock
│
├── Vue 3 前端
│   ├── 页面
│   ├── UI 组件
│   ├── 状态管理
│   └── SQL 编辑器
│
├── Tauri Runtime
│   ├── 桌面窗口
│   ├── IPC
│   ├── 系统能力
│   └── 应用配置
│
└── Rust Backend
    ├── 数据源管理
    ├── MySQL Adapter
    ├── SQLite
    ├── SQL 执行
    ├── 任务管理
    └── 系统凭据管理
```

最终构建产物包含：

- 前端静态资源。
- Rust 编译产物。
- Tauri 桌面应用运行所需资源。
- 对应操作系统的安装包。

用户不需要单独安装 Node.js、Rust 或 MySQL 客户端才能运行 DataDock。

MySQL 服务由用户自行提供，DataDock 负责连接远程或本地 MySQL 服务。

## 2.2 构建原则

1. 开发环境与生产环境配置分离。
2. 生产构建不能依赖开发服务器。
3. 不将开发调试配置打入正式版本。
4. 不将数据库密码写入构建产物。
5. 不将测试数据库连接信息打入正式版本。
6. 不将本地 SQLite 测试数据打入安装包。
7. 所有平台构建必须使用对应平台的构建环境。
8. 发布版本必须经过安装和实际运行测试。

# 3. 开发环境要求

## 3.1 通用开发环境

建议使用：

| 工具      | 用途               | 说明                   |
| --------- | ------------------ | ---------------------- |
| Node.js   | 前端运行环境       | 使用项目锁定的版本     |
| npm       | 前端依赖管理       | 默认使用 npm           |
| Rust      | 后端开发           | 使用 rustup 管理       |
| Cargo     | Rust 依赖和构建    | 随 Rust 工具链提供     |
| Tauri CLI | 桌面应用开发和构建 | 与项目依赖版本保持一致 |
| Git       | 版本管理           | 必需                   |
| MySQL     | 数据库测试         | 使用独立测试环境       |
| SQLite    | 本地数据存储       | 由 Rust 后端使用       |

具体版本以项目实际依赖和锁定文件为准。

如果后续决定更换包管理器，应同步调整项目文档和构建脚本。

## 3.2 Node.js 环境

前端使用 Vue 3 和 Vite。

需要安装：

- Node.js。
- npm。

建议通过版本管理工具管理 Node.js 版本。

项目应保留依赖锁定文件，例如：

```
package.json
package-lock.json
```

开发和 CI 环境优先使用：

```
npm ci
```

而不是每次使用 `npm install` 重新解析依赖。

这样可以尽可能保证不同环境安装的依赖版本一致。

## 3.3 Rust 环境

Rust 使用 rustup 管理工具链。

需要安装：

- rustc。
- cargo。
- rustfmt。
- clippy。

常见检查：

```
rustc --version
cargo --version
rustfmt --version
cargo clippy --version
```

项目应根据实际兼容性选择稳定版 Rust 工具链。

如果项目需要固定工具链版本，可以在仓库中添加：

```
rust-toolchain.toml
```

不应在没有必要的情况下随意切换 Rust 工具链。

## 3.4 Tauri 环境

需要根据实际使用的 Tauri 版本安装对应的开发依赖。

包括：

- Tauri 前端依赖。
- Rust Tauri 依赖。
- 对应操作系统的原生构建依赖。
- Tauri CLI。

Tauri 版本应与前端插件和 Rust 依赖保持兼容。

不要将 Tauri 1.x 和 Tauri 2.x 的配置方式混合使用。

如果项目采用 Tauri 2.x，应以对应版本的官方配置和 API 为准。

- Rust。
- Cargo。


```
node -v
npm -v

rustc --version
cargo --version

git --version
```

检查环境是否正常后，进入项目目录。

## 4.3 安装依赖

```

```

如果项目采用了不同的包管理器，以项目实际配置为准。

## 4.4 启动开发环境

```
npm run tauri dev
```

如果项目脚本名称不同，应以 `package.json` 中的实际配置为准。

开发模式应同时启动：

- Vite 开发服务器。
- Tauri 桌面窗口。
- Rust 后端。

## 4.5 macOS 凭据管理

macOS 下使用 Keychain 作为系统凭据管理方案。

测试内容：

- 保存数据库密码。
- 读取数据库密码。
- 更新数据库密码。
- 删除数据库密码。
- 应用重启后重新读取。
- 不同应用构建版本之间的凭据访问行为。

需要注意：

应用签名、Bundle Identifier 和访问组等配置可能影响 Keychain 凭据的访问行为。

正式发布前必须验证：

- 开发版本创建的凭据是否能被正式版本读取。
- 正式版本升级后是否仍然能读取原凭据。
- 应用重新签名后凭据访问是否正常。

不能只验证开发模式下的 Keychain 能力。

# 6. 项目构建配置

## 6.1 前端构建配置

前端使用 Vite 构建。

建议区分：

- development。
- production。
- test。

生产构建需要确保：

- 使用生产环境变量。
- 不启用开发调试功能。
- 不输出敏感调试信息。
- 不包含测试连接配置。
- 不包含开发环境专用文件。
- 静态资源路径适用于 Tauri 运行环境。

## 6.2 Rust 构建配置

Rust 负责：

- 数据库连接。
- SQLite 操作。
- 系统凭据管理。
- SQL 执行。
- 文件导出。
- 任务管理。

正式构建应使用生产构建配置。

建议通过 Cargo 的 release profile 生成优化产物。

是否需要进一步配置 LTO、代码优化等级和符号信息，应结合构建耗时、安装包大小和运行性能决定。

不能为了缩小安装包而使用未经验证的激进优化参数。

## 6.3 Tauri 配置

Tauri 配置至少需要明确：

- 产品名称。
- 产品版本。
- 应用标识。
- 窗口配置。
- 前端资源路径。
- 图标资源。
- 安装包类型。
- 权限和插件配置。

示意：

```
src-tauri/
├── capabilities/
├── icons/
├── src/
│   └── main.rs
├── Cargo.toml
├── Cargo.lock
└── tauri.conf.json
```

实际目录以所使用的 Tauri 版本为准。

## 6.4 应用标识

建议采用稳定且唯一的 Bundle Identifier。

例如：

```
com.datadock.app
```

该名称只是建议值，正式确定后应保持稳定。

应用标识可能影响：

- macOS 应用数据目录。
- Keychain 凭据访问。
- Windows 应用标识。
- 应用升级识别。
- 自动更新配置。

一旦正式发布，不应随意修改应用标识。

# 8. 安装包生成

## 8.1 macOS 安装包

根据 Tauri 当前版本和目标平台配置生成适合 macOS 的安装包。

常见形式：

- `.app`。
- `.dmg`。

需要验证：

- 安装包能够正常打开。
- 应用能够正常启动。
- 应用图标正确。
- 应用名称正确。
- Keychain 正常。
- SQLite 正常。
- MySQL 连接正常。
- 文件导出正常。

## 8.2 Windows 安装包

根据实际 Tauri 配置生成 Windows 安装包。

常见形式：

- `.msi`。
- `.exe` 安装程序。

具体类型由项目采用的 Tauri 打包方式决定。

需要验证：

- 安装程序正常运行。
- 安装目录正确。
- 应用可以启动。
- Credential Manager 正常。
- SQLite 正常。
- MySQL 连接正常。
- 文件导出正常。
- 卸载流程正常。

## 8.3 安装包命名

建议统一命名：

```
DataDock-{version}-{platform}-{arch}.{ext}
```

例如：

```
DataDock-1.0.0-macos-arm64.dmg
DataDock-1.0.0-windows-x64.msi
```

如果实际构建目标或安装包格式不同，应使用对应名称。

命名规则一经确定，应保持版本间一致。

## 8.4 架构支持

macOS 需要明确是否支持：

- Apple Silicon。
- Intel。

Windows 需要明确：

- x64。
- ARM64（如计划支持）。

不能因为源码理论上兼容，就直接宣称对应架构已经支持。

每种目标架构都必须经过实际构建和运行测试。

# 9. 应用本地数据和配置管理

## 9.1 本地数据目录

DataDock 使用 SQLite 保存本地数据。

建议将数据库文件放在操作系统提供的应用数据目录中。

不能将用户数据放在：

- 项目源码目录。
- 安装目录。
- 应用可执行文件同级目录。
- 临时目录。

实际目录应由 Tauri 的应用数据目录 API 获取。

## 9.2 数据目录内容

建议结构：

```
DataDock/
├── datadock.db
├── logs/
├── exports/
└── backups/
```

上述是逻辑结构示例，实际目录名称和位置由应用配置决定。

## 9.3 数据迁移

应用升级时，本地 SQLite 数据可能需要升级。

必须采用版本化 Migration。

升级流程：

```
启动应用
    |
    v
检查本地数据库
    |
    v
读取当前数据库版本
    |
    v
比较应用目标版本
    |
    v
执行必要的 Migration
    |
    v
验证迁移结果
    |
    v
启动应用
```

如果 Migration 失败：

- 不得直接删除原数据库。
- 不得静默忽略迁移失败。
- 应保留必要的错误日志。
- 应提供明确错误提示。
- 应在必要时阻止进入可能破坏数据的操作。

## 9.4 用户数据保留

普通应用升级不应删除：

- 数据源配置。
- SQL 查询历史。
- SQL 收藏。
- 应用设置。
- 工作区状态。

应用卸载是否保留用户数据，应遵循操作系统和安装方式的实际行为，并在用户文档中明确说明。

# 10. 应用版本管理

## 10.1 版本号格式

建议采用语义化版本：

```
MAJOR.MINOR.PATCH
```

例如：

```
1.0.0
1.0.1
1.1.0
2.0.0
```

含义：

| 版本部分 | 说明               |
| -------- | ------------------ |
| MAJOR    | 不兼容的重大变化   |
| MINOR    | 新增兼容功能       |
| PATCH    | 问题修复和小幅优化 |

## 10.2 版本号管理

项目需要保证以下位置的版本号一致：

- `package.json`。
- Tauri 应用配置。
- Rust Cargo 配置。
- 发布说明。

如果实际项目采用统一版本管理工具，可以减少人工维护。

不能出现安装包版本号与应用内部版本号不一致的情况。

## 10.3 开发版本

开发过程中可以使用：

```
1.0.0-alpha.1
1.0.0-alpha.2
1.0.0-beta.1
1.0.0-rc.1
```

正式发布前应完成必要的回归测试。

## 10.4 发布版本

正式版本采用：

```
1.0.0
```

发布后不应覆盖已经发布的版本文件。

如果发现问题，应发布新的 PATCH 版本。

# 11. Git 分支和提交规范

## 11.1 分支管理

建议使用简单分支策略：

```
main
  |
  ├── develop
  |
  ├── feature/*
  |
  ├── fix/*
  |
  └── release/*
```

分支说明：

| 分支    | 用途         |
| ------- | ------------ |
| main    | 稳定正式版本 |
| develop | 日常集成开发 |
| feature | 新功能       |
| fix     | 问题修复     |
| release | 发布准备     |

如果项目由个人独立开发，可以采用更简单的 main + feature 分支策略，不必为了形式引入复杂分支管理。

## 11.2 提交信息

建议使用：

```
feat: 新增 MySQL 连接管理
fix: 修复 SQL 执行结果显示问题
refactor: 重构连接管理模块
docs: 更新技术架构文档
test: 增加数据浏览器测试
build: 调整 Tauri 构建配置
chore: 更新项目依赖
```

提交信息应明确表达本次修改内容。

## 11.3 发布前 Git 检查

正式构建前检查：

```
git status
git branch --show-current
git log -5 --oneline
```

确保：

- 工作区不存在未处理的修改。
- 当前分支符合发布要求。
- 代码已经提交。
- 版本号已经更新。

# 12. CI/CD 自动化构建

## 12.1 自动化目标

后续可以使用 GitHub Actions 或其他 CI 平台实现自动化构建。

目标：

- 自动安装依赖。
- 自动执行前端检查。
- 自动执行 Rust 检查。
- 自动执行测试。
- 自动构建桌面应用。
- 自动生成安装包。
- 自动上传构建产物。

CI 平台不是 V1.0 功能开发的前置条件。

## 12.2 构建矩阵

建议后续采用平台构建矩阵：

| 平台    | 构建目标          |
| ------- | ----------------- |
| macOS   | Apple Silicon     |
| macOS   | Intel（如果支持） |
| Windows | x64               |
| Windows | ARM64（如果支持） |

不同平台应使用对应的 Runner。

不能默认在 macOS 上直接生成可在 Windows 正常运行的最终安装包。

## 12.3 CI 执行步骤

```
代码提交
    |
    v
触发 CI
    |
    v
安装 Node.js
    |
    v
安装 Rust
    |
    v
安装系统依赖
    |
    v
安装前端依赖
    |
    v
前端检查
    |
    v
Rust 检查
    |
    v
自动化测试
    |
    v
桌面应用构建
    |
    v
上传构建产物
```

## 12.4 CI 安全要求

CI 环境不得保存真实数据库密码。

需要连接测试数据库时，应使用独立测试环境和专门测试账号。

任何真实凭据都不得提交到 Git 仓库。

# 13. 代码签名与分发

## 13.1 macOS 签名

正式对外分发 macOS 应用时，需要评估：

- Developer ID Application 签名。
- Hardened Runtime。
- Notarization 公证。
- 安装包签名。

具体要求根据分发方式和 Apple 当前规则确定。

如果暂时没有完成签名和公证，应明确标注应用的分发限制。

不能将未签名构建描述为已经具备完整的正式分发体验。

## 13.2 Windows 签名

Windows 正式分发时，可以评估代码签名证书。

需要关注：

- 安装包签名。
- 可执行文件签名。
- 证书有效期。
- 安装来源信誉。
- 安全软件误报。

是否使用签名证书属于正式发布策略，需要结合分发范围和成本决定。

## 13.3 签名密钥安全

签名证书和私钥不能提交到 Git 仓库。

如果使用 CI：

- 使用 CI Secret。
- 限制访问权限。
- 不在构建日志中输出密钥。
- 只允许受信任的发布流程使用签名密钥。

# 17. 构建问题排查

## 17.1 前端构建失败

检查：

- Node.js 版本。
- npm 版本。
- 依赖锁定文件。
- TypeScript 错误。
- Vite 配置。
- 环境变量。
- Monaco Editor 资源加载。

## 17.2 Rust 构建失败

检查：

- Rust 工具链。
- Cargo.lock。
- 系统编译依赖。
- Tauri 版本兼容性。
- 原生库依赖。
- 平台特定 Feature。
- 编译错误日志。

## 17.3 Tauri 打包失败

检查：

- Tauri 配置文件。
- 图标资源。
- 应用标识。
- 前端构建路径。
- 平台 SDK。
- 安装包配置。
- 系统签名配置。

## 17.4 应用安装后无法启动

重点检查：

- 运行时依赖。
- WebView2。
- 系统权限。
- 应用资源路径。
- SQLite 数据目录。
- 凭据访问权限。
- 动态库依赖。
- 启动日志。

## 17.5 凭据在正式版本中无法读取

重点检查：

- Bundle Identifier。
- 签名身份。
- 凭据名称和引用。
- Keychain Access Group。
- Windows 用户上下文。
- 凭据服务权限。
- 安装和升级方式。

不要在正式版本中通过明文保存密码来绕过系统凭据访问问题。

# 18. AI 构建执行规范

AI 在处理 DataDock 构建、打包和发布任务时，必须遵循以下要求。

## 18.1 构建前检查

先确认：

1. 当前项目使用的 Tauri 版本。
2. 当前 Node.js 版本。
3. 当前 Rust 工具链。
4. package.json 中的构建脚本。
5. Tauri 配置文件。
6. 目标操作系统。
7. 目标架构。
8. 当前 Git 工作区状态。

不得根据其他版本 Tauri 的经验直接修改当前项目配置。

## 18.2 执行构建

构建时必须：

- 使用项目锁定的依赖。
- 执行前端检查。
- 执行 Rust 检查。
- 执行必要测试。
- 记录构建命令。
- 记录构建结果。

## 18.3 构建失败

如果构建失败：

1. 获取完整错误信息。
2. 判断属于环境问题还是代码问题。
3. 确认影响范围。
4. 提出修复方案。
5. 修复后重新执行检查。

禁止直接删除依赖、修改版本或大范围重构来掩盖构建问题。

## 18.4 发布任务

没有明确发布授权时，AI 不得擅自：

- 发布正式版本。
- 上传安装包到公共平台。
- 创建公开 Release。
- 修改线上更新地址。
- 删除已有发布文件。

构建本地安装包与正式发布是两个不同操作。

# 20. 最终实施原则

DataDock 的构建和发布必须遵循以下原则：

1. 开发环境可运行，不代表生产构建一定可用。
2. 构建成功，不代表安装包已经通过测试。
3. 安装包能够启动，不代表所有核心功能都正常。
4. 本地升级不能破坏用户数据。
5. 数据库密码必须通过系统凭据管理机制保护。
6. 不同操作系统必须分别验证。
7. 正式发布必须有明确版本号和发布记录。
8. 所有构建结果必须可追溯。

**最终目标：让 DataDock 的开发、构建、安装和升级过程稳定、可重复，并保证用户的本地数据和数据库凭据安全。**
